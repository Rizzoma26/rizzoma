# Скилл 04 — миграция удаления beta_settings

**Запуск:** «выполни скилл `beta-config-04-drop-migration`». **Требует:** решение B, `.agents/skills/beta-config-03-remove-write-path/SKILL.md` завершён, записан результат `.agents/skills/beta-config-02-capture-values/SKILL.md`. **Меняет:** новый файл `db/migrations/003_drop_beta_settings.sql` и документацию о схеме. **Не меняет** `002_persistent_bot_state.sql`, контуры и их данные.

## Цель

ТЗ, п. 4: добавить новую миграцию для удаления `beta_settings`; уже применённую `002_persistent_bot_state.sql` не редактировать.

## Почему нельзя трогать `002`

Раннер `apps/api/src/db/migrate.ts` сортирует файлы по имени и хранит SHA-256 каждого применённого файла в `schema_migrations`. Если содержимое применённого файла изменилось, он падает с ошибкой `Migration checksum mismatch` и именем файла, и API не запустится ни в одном контуре, где `002` уже применена. Отсюда же нумерация: следующий файл — `003_*.sql`.

## Предусловия

**Стоп-условия:**
- Скилл 03 не завершён: код всё ещё обращается к `beta_settings` (`grep -rn "beta_settings" bot/` должен быть пуст).
- Нет записи эффективных значений из скилла 02. Удаление таблицы **необратимо потеряет** значение и след «кто и когда менял» (`updated_by_telegram_user_id`, `updated_at`).
- Файл `db/migrations/003_*` уже существует в любой ветке — не создавать второй с тем же номером, разобраться.
- `002_persistent_bot_state.sql` менялся в `git log` после первого коммита или его `git diff` не пуст — это **CONTRADICTION**, остановиться.
- Миграцию нужно применить к контуру, где ещё работает код, читающий таблицу (см. «Порядок выкладки»).

Проверки только на чтение:

```bash
ls db/migrations/
git log --oneline -- db/migrations/002_persistent_bot_state.sql
git diff --stat -- db/migrations/002_persistent_bot_state.sql
git ls-remote --heads origin
```

Последняя команда — чтение, не запись; если сеть недоступна, её можно пропустить и сказать об этом в отчёте.

## Шаги

1. Создать `db/migrations/003_drop_beta_settings.sql`:

```sql
-- beta_settings was replaced by the server-side beta configuration module.
-- Applied migrations are immutable: this file only drops the obsolete table.
DROP TABLE beta_settings;
```

   Без `IF EXISTS`: таблица создаётся в `002`, а раннер применяет файлы по порядку — её отсутствие означало бы дрейф схемы, и падение лучше, чем тишина. Раннер выполняет каждый файл в транзакции под advisory lock.
2. Обновить документацию **о схеме**: `docs/data-and-idempotency.md` (миграция `002` добавляла `beta_settings`, `003` её удаляет; про `beta_settings` говорить в прошедшем времени), `docs/project-guide.md` (PostgreSQL больше не хранит «общие настройки беты»), README (строка `DATABASE_URL`: применённые миграции `001`, `002`, `003`). Исторические записи вроде «оба контура применили две миграции» в `docs/environments.md` не править — это описание прошлого прогона.
3. Проверить на **одноразовой** БД (не на dev и не на prod).

## Проверка на одноразовой БД

Создать контейнер только для этой проверки. Пароль случайный и нигде не печатается.

```bash
PW=$(openssl rand -hex 12)
docker run -d --rm --name rizzoma-scratch-pg -e POSTGRES_PASSWORD="$PW" -p 127.0.0.1:55432:5432 postgres:16-alpine
```

Раннер читает `config.ts`, которому нужны все обязательные переменные. Задать их явно синтетическими значениями — они перекрывают возможный `.env` (dotenv не перезаписывает уже заданные переменные):

```bash
APP_ENV=dev DEV_ALLOWED_TG_IDS=1 BOT_TOKEN=scratch-token-0000000000 \
ALLOWED_ORIGINS=https://scratch.invalid \
DATABASE_URL="postgresql://postgres:$PW@127.0.0.1:55432/postgres" \
npm run db:migrate
```

Случаи:

| № | Что проверить | Как | Ожидается |
|---|---|---|---|
| a | Чистая БД | запустить раннер | применены `001`, `002`, `003`; таблицы `beta_settings` нет; в `schema_migrations` три записи |
| b | Путь обновления | временно убрать `003` из каталога (файл ещё не закоммичен), запустить раннер, вставить строку в `beta_settings` и несколько тестовых строк в пользовательские таблицы, записать число строк и контрольную сумму `002` из `schema_migrations`; вернуть файл, запустить раннер | применяется только `003`; таблица удалена; контрольная сумма `002` прежняя; число строк в остальных таблицах прежнее |
| c | Идемпотентность | запустить раннер ещё раз | ничего не применяется, ошибок нет |
| d | Порядок выкладки | (по желанию) вызвать старый код чтения таблицы против схемы после `003` | ошибка о том, что отношение `beta_settings` не существует — это и есть причина порядка ниже |

После проверки убрать **только** созданный контейнер: `docker rm -f rizzoma-scratch-pg`. Убедиться, что `git status` показывает `003` так же, как до шага b.

## Порядок выкладки

- **Код раньше миграции.** Старый бот при запуске выполняет `INSERT INTO beta_settings` и читает таблицу в `/api/state`. Если раннер удалит таблицу, пока в контуре ещё работает старый бот, тот получит ошибку. `docker compose up -d` пересоздаёт сервисы не одновременно, а API применяет миграции при старте своего контейнера — окно с ошибками реально.
- **По умолчанию две поставки:** сначала релиз с кодом из скиллов 01 и 03 (таблица остаётся неиспользуемой), затем релиз с миграцией `003`. Одна поставка допустима только для контура без трафика — решать явно и записать в отчёт.
- **Порядок контуров:** dev, затем prod (`docs/environments.md`: изменения схемы сначала проверяются на dev).
- **prod:** перед миграцией резервная копия по `docs/environments.md` (`pg_dump -Fc` под `umask 077`, проверка кода завершения, пробное восстановление в отдельную БД). Не продолжать, если резервная копия не удалась.
- **Откат.** Раннер идёт только вперёд. Вернуть таблицу можно новой миграцией `004_*` (структура из `002`: `id integer PRIMARY KEY CHECK (id = 1)`, `beta_open smallint[] NOT NULL`, `updated_by_telegram_user_id bigint`, `updated_at timestamptz NOT NULL DEFAULT now()`) со вставкой значения, записанного в скилле 02, либо восстановлением из резервной копии. Не делать без отдельной просьбы.

## Отчёт

Имя и содержимое миграции; результаты случаев a–d; подтверждение, что `002` не менялась; принятое решение о поставке (одна или две) и порядок контуров; ограничения: миграция к dev и prod **не применялась**, реальные контуры не проверялись.

## Чего не делать

- Не редактировать `002_persistent_bot_state.sql`, не переименовывать применённые файлы.
- Не запускать `npm run db:migrate` без явно заданного `DATABASE_URL` одноразовой БД: раннер применяет изменения по-настоящему и может подхватить `.env` с реальным контуром.
- Не применять миграцию к dev или prod в рамках этого скилла и не печатать значения env и `DATABASE_URL`.
- Не удалять volumes и контейнеры контуров.
