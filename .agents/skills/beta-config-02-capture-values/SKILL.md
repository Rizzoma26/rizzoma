# Скилл 02 — эффективные значения беты в dev и prod

**Запуск:** «выполни скилл `beta-config-02-capture-values`». **Требует:** решение B в `.agents/skills/beta-config-00-decision-gate/SKILL.md`. **Меняет:** ничего, пока идёт чтение; в финале — env-файл контура, **только по отдельному подтверждению** владельца. Должен завершиться до деплоя модуля из `.agents/skills/beta-config-01-server-module/SKILL.md` и до `.agents/skills/beta-config-05-acceptance-check/SKILL.md`.

## Цель

ТЗ, п. 2: до переноса прочитать текущую настройку отдельно в dev и prod и зафиксировать их эффективные значения в конфигурации каждого контура.

## Что считать «эффективным значением»

Так устроено в коде (`bot/bot.js`, `bot/storage.js`, `feat/app@ea5c530`):

1. **Строка `beta_settings`** — источник истины: именно её отдаёт `/api/state`.
2. Строка создаётся при первом запуске бота: `INSERT INTO beta_settings (id, beta_open) VALUES (1, …) ON CONFLICT (id) DO NOTHING`. Значение берётся из env `BETA_OPEN`, а если оно пусто или невалидно — из `economy.js` (`BETA_OPEN`, сейчас `0,1,3,4`).
3. После создания строки env и значение по умолчанию **игнорируются**. Поэтому env может расходиться с реальным значением: в dev — если админ менял через панель, в prod — если env правили после первого запуска.

Итог: эффективное значение = значение из строки БД. Если таблицы или строки ещё нет — «не создано»; будущее значение тогда будет из env (если задан и валиден), иначе по умолчанию. Перенос обязан сохранить **наблюдаемое** значение, а не env и не значение по умолчанию.

## Предусловия

**Стоп-условия:**
- Нет решения B.
- Неизвестно, какие контуры реально существуют и есть ли к ним доступ. `docs/environments.md` сообщает, что реальное развёртывание не выполнено. Хосты, пути и учётные данные не угадывать — запросить у владельца. Нет контура или доступа — записать «не измерено», а значение вывести из env-шаблона и значения по умолчанию, пометив **«выведено, не измерено»**.
- Prod читать только с явного согласия владельца и отдельным шагом после dev.
- Проект compose не соответствует контуру (см. шаг 2) — остановиться.

## Правила безопасности

- Только чтение. SQL — `SELECT` в сессии с `SET default_transaction_read_only = on`.
- dev и prod — отдельные команды с явным `--env-file` каждого; не подключаться к двум БД из одной сессии, не копировать данные prod в dev.
- Не выводить env целиком. Значение `BETA_OPEN` разрешено показать после нормализации (публичные индексы, они и так уходят клиентам в `/api/state`); остальные переменные — только «задано» / «не задано».
- `updated_by_telegram_user_id` не печатать: достаточно факта «менялось админом» (значение не NULL).
- Не запускать миграции и `npm run db:migrate`.

## Шаги (для каждого контура отдельно, сначала dev)

1. **Контур.** `ENVFILE=/etc/rizzoma/dev.env` (для prod — `prod.env`). Проверить, что `APP_ENV` в файле ожидаемый: `grep -E '^APP_ENV=' "$ENVFILE"` (значение `dev` или `prod` выводить можно).
2. **Проект compose.** `docker compose --env-file "$ENVFILE" ps` — в именах должно быть `rizzoma-dev` (или `rizzoma-prod`). Иначе стоп: это чужой контур.
3. **Применены ли миграции.**

```bash
docker compose --env-file "$ENVFILE" exec -T postgres sh -c 'psql -X -A -t -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SET default_transaction_read_only = on;
SELECT name FROM schema_migrations ORDER BY name;
SQL
```

   Нет `002_persistent_bot_state.sql` — таблицы `beta_settings` нет: перейти к шагу 5 с пометкой «не создано».
4. **Строка беты.**

```bash
docker compose --env-file "$ENVFILE" exec -T postgres sh -c 'psql -X -A -t -F "|" -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SET default_transaction_read_only = on;
SELECT beta_open, (updated_by_telegram_user_id IS NOT NULL) AS changed_by_admin, updated_at FROM beta_settings WHERE id = 1;
SQL
```

   Ожидается 0 или 1 строка: ограничение `CHECK (id = 1)` не допускает большего.
5. **Env.** Статус переменных `BETA_OPEN`, `QA_ENABLED`, `ADMIN_TG_IDS` — «задано» / «не задано» (например, `grep -qE '^BETA_OPEN=.+' "$ENVFILE"`). Значение `BETA_OPEN`, если задано, нормализовать (целые по возрастанию) и показать; невалидное — «невалидно», без вывода остального.
6. **Сравнить** три величины: строка БД, env, значение по умолчанию из `economy.js`. Расхождение оформить как **CONTRADICTION**: наблюдаемое (БД) / документированное (env) / предлагаемое (записать наблюдаемое).
7. **Отчёт** — таблица ниже. Контур закончен — переходить к следующему.
8. **Запись в конфигурацию контура** (после того, как измерены оба контура или явно решено, что одного достаточно, и после подтверждения владельца по каждому контуру отдельно): записать эффективное значение в `BETA_OPEN` env-файла контура. Перед правкой — резервная копия файла с теми же правами (`cp -p`), после — `docker compose --env-file "$ENVFILE" config --quiet`. Контейнеры сейчас **не пересоздавать**: пока источник истины БД, env ничего не меняет, а пересоздание понадобится при выкладке скиллов 01 и 03.

## Чего не делать

- Не менять данные и схему, не пересоздавать контейнеры, не удалять volumes.
- Не печатать `DATABASE_URL`, токены, `initData`, id админа и содержимое env-файлов.
- Не смешивать контуры и не считать значение по умолчанию наблюдением.
- Не править env prod без подтверждения владельца именно на prod.
