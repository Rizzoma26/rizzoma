# Архитектура Rizzoma

1. Прочитайте затронутый вход и ближайшие зависимости текущего кода. Для API начните с `apps/api/src/app.ts`, для границы web/API — с фактического вызывающего frontend-кода и `packages`; не читайте все компоненты заранее.
2. Восстановите существующие responsibilities и путь данных. Выберите минимальное изменение внутри действующих границ. Не дробите весь frontend и не вводите новый framework ради одной функции.
3. Только если нужно понять прежнее решение или требование, используйте Knowledge-маршрут из AGENTS.md. Для решения по средам точечно прочитайте `docs/environments.md`, отделяя целевую модель от кода.
4. Дайте краткое предложение: изменяемые компоненты, поток данных и API-контракт, влияние на БД/миграции, failure modes и Docker/deployment. Укажите реальные tradeoffs и неизвестные; не перепроектируйте незатронутые части.
5. Для реализации подключите профильный skill лишь для выбранного изменения: HTTP, PostgreSQL или Docker. Предложите проверку наблюдаемого поведения и при необходимости способ обратимого выпуска.

Наличие proposal не требует отдельного согласования, если реализация уже входит в запрос пользователя; не расширяйте разрешённую область работ.
