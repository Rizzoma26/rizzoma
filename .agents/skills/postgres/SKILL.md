# PostgreSQL Rizzoma

1. Найдите затронутый repository и SQL. API использует `pg`: `apps/api/src/db/pool.ts`, например `auth/auth.repository.ts`; для bot сначала проверьте его существующий DB layer. Не добавляйте ORM, второй пул или SQLite fallback без обоснованной необходимости.
2. Значения передавайте параметрами запроса; динамические идентификаторы ограничивайте allowlist. Проверяйте число запросов/N+1, нужные индексы, unique/FK constraints и конкурентные обновления.
3. Связанные записи выполняйте одной транзакцией на одном выделенном client с rollback и release. Учитывайте идемпотентность регистрации/платежей, когда они затронуты. План запроса проверяйте на dev; `EXPLAIN ANALYZE` реально исполняет запрос.
4. Изменения схемы добавляйте в `db/migrations/*.sql` следующей версией. Runner `apps/api/src/db/migrate.ts` сортирует файлы, проверяет SHA-256, держит advisory lock и выполняет каждый файл в транзакции. Операции вроде `CREATE INDEX CONCURRENTLY` несовместимы с этой транзакцией: сначала спроектируйте подходящий путь, не вставляйте их в обычную миграцию.
5. Перед destructive DDL оцените данные, длительность блокировки, совместимость старой/новой сборки, backup и восстановление; проверьте на отдельной dev БД. Не запускайте миграцию на prod как часть локальной проверки.
6. Сверьте SQL и targeted repository-тест; для новой миграции на dev проверьте применение, результат и повторный запуск runner без повторных изменений. `npm run db:migrate` выполняет реальные изменения: сначала убедитесь, какой контур выбран, не выводя DATABASE_URL.
