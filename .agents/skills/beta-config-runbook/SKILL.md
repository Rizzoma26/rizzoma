# Rizzoma: перенос настройки беты и вынос статических данных

Набор из семи скиллов по ТЗ «условный перенос настройки беты в серверный модуль и вынесение статических данных из `index.html`» (текст ТЗ вставлен пользователем 2026-09-29). Пункты 1–6 ТЗ соответствуют скиллам 01–06. Скилл 00 добавлен из самого ТЗ: оно начинается с условия («переносить `beta_settings` в скрипт стоит, только если бета должна меняться вместе с релизом, а не через админку») и «решения по умолчанию». Их нужно зафиксировать явно до любых правок.

**Статус:**
Скиллы написаны, но ни разу не запускались. Создание этих файлов ничего не меняет ни в остальном репозитории, ни на серверах.

## Как запускать

- Команда: «выполни скилл `<skill_name>`» — имя указано в frontmatter каждого файла и в таблице ниже. Один скилл за раз.
- В конце каждого скилла — отчёт «проверено / ограничения». Следующий скилл — только после подтверждения владельца.
- Каждый файл самодостаточен: предусловия, стоп-условия, шаги, проверки, чего не делать. Формат уже соответствует проектным skills репозитория (`name` + `description` + шаги).

## Жёсткие зависимости

1. Скилл 00 решает, запускать ли 01–05. Без явного ответа действует значение по умолчанию из ТЗ: `beta_settings` остаётся в БД, скиллы 01–05 не запускаются.
2. Скилл 02 (только чтение) должен завершиться **до любого деплоя** модуля из скилла 01 и до сравнения «API отдаёт прежний список» в скилле 05: без записанных эффективных значений нечем подтвердить, что список не изменился.
3. Скилл 03 требует готового модуля из скилла 01.
4. Миграцию из скилла 04 можно **написать** сразу после 03, но **применять** к контуру только после того, как код без обращений к `beta_settings` уже работает в этом контуре. Иначе старый бот обратится к удалённой таблице.
5. Скилл 05 требует базовых значений из 02 и результатов 01, 03, 04.
6. Скилл 06 не зависит от остальных. Данные, которые он выносит, не зависят от контура — список открытых узлов беты в них попадать не должен.

## CONTRADICTION (наблюдаемое / документированное / предлагаемое)

1. **Какой репозиторий.**
   Наблюдаемое: локальная копия `M:\rizzoma\site` стоит на `main` (`082edc9`) и не содержит `beta_settings`, миграций, `bot/storage.js`, контуров dev/prod. На GitHub ветка `feat/app` (`ea5c530`, пять коммитов автора KrasyukDS от 2026-09-26…29 поверх `main`) всё это содержит.
   Документированное: ТЗ ссылается на `002_persistent_bot_state.sql` и на dev/prod.
   Предлагаемое: выполнять скиллы на checkout ветки `feat/app` (при необходимости отдельным worktree), ветку пользователя без его согласия не переключать.
2. **Где реально меняется бета.**
   Наблюдаемое: `adminAuth` требует `QA_ENABLED`, а он допустим только в dev (запуск prod с `QA_ENABLED=true` останавливает бота). В режиме БД `BETA_OPEN` читается только при первом создании строки.
   Документированное: README — «из бета-админки туман правится на лету, без деплоя».
   Предлагаемое: считать сценарий «менять без деплоя» реальным только для dev; учесть в скилле 00.
3. **Готовность контуров.**
   Наблюдаемое: `docs/environments.md` сообщает, что реальное развёртывание не выполнено.
   ТЗ: «прочитать текущую настройку отдельно в dev и prod».
   Предлагаемое: скилл 02 различает «измерено» и «выведено из env или значения по умолчанию» и не подставляет догадки.
4. **Версия Node (вне ТЗ).**
   Наблюдаемое: CI использует `node-version: 20`, а `package.json` требует `>=22.22.2`, Dockerfile — `node:22.22.2`.
   Предлагаемое: в рамках этих скиллов не исправлять, но помнить при чтении результата CI.

## Общие правила (из `AGENTS.md` репозитория)

- Перед правками — `git status` и текущая ветка; чужие изменения сохранять. Удалённый Git (push, PR) — только по отдельной просьбе владельца.
- Применённые миграции неизменны. dev и prod не делят состояние и секреты. Защищённый UI и API требуют серверную Telegram-авторизацию и сессию, dev — allowlist. QA и тестовые платежи — только dev.
- Не выводить значения env, credentials, токены, `initData`, платёжные данные — только имена и статус «задано» или «не задано». Единственное исключение — значение самой беты (см. скилл 02): это публичные индексы, они и так уходят клиентам в `/api/state`.
- Контекст: один подходящий проектный skill из `.agents/skills/`, затем нужные файлы, затем точечная проверка; второй skill — только по необходимости.
- Расхождения маркировать **CONTRADICTION**: наблюдаемое / документированное / предлагаемое.
- Проверки по слою: `node --test tests/<file>.test.mjs`, `npm run typecheck`, `npm run build`, `npx playwright test tests/e2e/<file>.spec.mjs`; полный `npm test` — при широком влиянии.
- В отчёте — что проверено и ограничения. Развёртывание не объявлять готовым по одним шаблонам.
- Перед передачей ветки: `npm run handoff` (обновляет `docs/handoffs/branch-context.md`) — только когда владелец просит передать ветку.

## Открытые вопросы к владельцу

1. Скилл 00: менять бету вместе с релизом или без деплоя через админку (по умолчанию — без деплоя, значит 01–05 не запускать).
2. Источник значений контура: переменная `BETA_OPEN` в env контура (по умолчанию) или константы в коде по `APP_ENV`.
3. Нужен ли dev способ менять бету без деплоя.
4. Строгость валидации: дубликаты и пустой список — ошибка (по умолчанию) или нормализация.
5. Поставка миграции: одной поставкой с кодом или двумя (по умолчанию две).
6. Скилл 06: порог, при котором вынос данных считается оправданным.
