# Скилл 00 — решение о переносе беты (gate)

**Запуск:** «выполни скилл `beta-config-00-decision-gate`». **Меняет:** ничего. **Результат:** одно из двух решений, записанное в отчёте. Порядок всех скиллов — в `.agents/skills/beta-config-runbook/SKILL.md`.

## Зачем

ТЗ: переносить `beta_settings` в скрипт стоит, только если бета должна меняться вместе с релизом, а не через админку. По умолчанию — пока админка должна менять бету без деплоя — `beta_settings` остаётся в БД: перенос меняет продуктовый сценарий, а не просто освобождает БД от лишних данных.

Без явного решения владельца действует значение по умолчанию: **скиллы 01–05 не запускаются**.

## Что известно из кода (наблюдалось на `feat/app`, `ea5c530`)

1. Бета лежит в таблице `beta_settings` (миграция `002_persistent_bot_state.sql`): одна строка `id = 1`, список открытых узлов `beta_open`, кто и когда менял.
2. Читает и пишет её бот: `/api/state` отдаёт список, `POST /api/admin/beta` меняет его, `/api/admin/overview` показывает. Клиент кэширует последний список в `rizzoma_beta`.
3. **Кто может менять.** `adminAuth` требует `QA_ENABLED`, а он допустим только в dev (запуск prod с `QA_ENABLED=true` останавливает бота), плюс `ADMIN_TG_IDS`, а в dev ещё allowlist тестеров. Значит, **в prod штатного пути изменения беты через приложение нет**.
4. **Что даёт env.** В режиме БД `BETA_OPEN` используется только при первом создании строки (`INSERT … ON CONFLICT DO NOTHING`). После этого изменение env ничего не меняет — README и `bot/.env.example` говорят то же.
5. **Как читается env.** `parseList` мягкий: неверные элементы молча отбрасываются, а если ничего не осталось, берётся значение по умолчанию из `economy.js`. Плохая настройка сегодня не останавливает запуск.
6. **Три источника.** По README набор открытых узлов задаётся в `economy.js` (`BETA_OPEN`), в публичном `config.js` (`betaOpen`) и на бэкенде (`BETA_OPEN`) — по возрастанию приоритета.

Вывод для решения: сценарий «менять без деплоя» сегодня реален только для dev; в prod бету можно изменить лишь прямым SQL. Это и есть аргумент за перенос. Аргумент против — потеря живого переключения в dev и необратимость удаления таблицы.

## Варианты

| | A. Оставить в БД (по умолчанию) | B. Перенести в серверный модуль |
|---|---|---|
| Как меняется бета в dev | админ через панель, без деплоя | деплоем с новым `BETA_OPEN` (пересоздание бота) |
| Как меняется бета в prod | штатного пути нет | деплоем |
| Источник истины | строка `beta_settings` | серверный модуль + env контура |
| Миграции | нет | новая `003_*` с удалением таблицы |
| Основной риск | расхождение env и БД остаётся | потеря живого переключения в dev, необратимый DROP, окно совместимости при выкатке |
| Пункты ТЗ | 1–5 не выполнять | выполнять скиллы 01–05 |

Гибрид (в dev оставить БД, в prod — модуль) в ТЗ не описан: два разных пути чтения в одном коде противоречат принципу «один проверяемый артефакт для dev и prod» из `docs/environments.md`. Если он нужен — это отдельное решение, а не часть этого скилла.

## Предусловия

**Стоп-условия:**
- Локальная копия не на `feat/app` (или потомке `ea5c530`): в `main` нет ни `beta_settings`, ни миграций, ни контуров — решение нельзя принимать по коду, которого нет. Сообщить владельцу и остановиться. Ветку самостоятельно не переключать и `git stash` не делать.
- Владелец не ответил явно — фиксировать вариант A и остановиться.

Проверка (только чтение): `git branch --show-current`, `git log -1 --format=%h`, `git status --short`.

## Шаги

1. Проверить ветку и коммит (см. выше).
2. Задать владельцу **один** вопрос: «Бета должна меняться вместе с релизом (без админ-контрола) или админ должен менять её без деплоя?» — вместе с таблицей вариантов и фактами 3–4 выше.
3. Нет явного ответа — записать вариант A и остановиться.
4. При выборе B подтвердить подрешения (в скобках — значение по умолчанию):
   - источник значений контура: переменная `BETA_OPEN` в env контура (по умолчанию) или константы в коде по `APP_ENV`;
   - нужен ли dev способ менять бету без деплоя (нет; меняется пересозданием бота с новым env);
   - строгость валидации: дубликаты и пустой список — ошибка (да);
   - поставка миграции: две — сначала код без обращений к `beta_settings`, затем `003` (две);
   - оставлять ли в админ-панели только чтение списка (да).
5. Записать решение и подрешения в отчёт.
6. Следующий шаг: при A — только `.agents/skills/beta-config-06-static-data/SKILL.md`; при B — скилл 02, затем 01 и далее по `.agents/skills/beta-config-runbook/SKILL.md`.

## Отчёт

- Решение: A или B; кто принял и когда (со слов владельца).
- Подрешения при B.
- Ветка и коммит, на которых проверялись факты.
- **CONTRADICTION**, если код расходится со снимком в runbook.
- Ограничения: факты 1–6 взяты из чтения кода, ни один контур не запускался.

## Чего не делать

- Не менять файлы, не запускать миграции, не подключаться к контурам.
- Не выбирать вариант B по умолчанию и не считать молчание согласием.
- Не путать «убрать `beta_settings` из БД» с «очистить лишние данные»: это изменение продуктового сценария.
