# Security review Rizzoma

1. Определите входные недоверенные данные, защищаемый ресурс и текущую серверную проверку. Читайте только затронутый путь. Выбирайте актуальные риски: SQL injection, XSS, CSRF, SSRF, broken authorization, credential leakage и небезопасные env/logging.
2. Для Telegram-входа проверьте `apps/api/src/auth/telegram-init-data.ts`, соответствующий service/маршрут; для защиты UI — `docker/nginx.conf` и bootstrap. `initDataUnsafe`, platform, User-Agent, CORS и скрытая кнопка не являются доказательством входа. Публичная стартовая оболочка передаёт подписанные данные, но не раскрывает защищённый UI.
3. Для session/cookie проверьте срок действия и отзыв, cookie flags, host scope и проверку на каждом защищённом запросе. При изменении cookie-auth оцените CSRF для операций записи; разные боты/контуры не должны принимать чужие подписи или сессии.
4. Для соответствующего изменения входа используйте `tests/auth.test.mjs`: валидная подпись, чужой бот, просрочка, отсутствие авторизации и пользователь вне dev allowlist. Проверка настоящих Mini Apps двух ботов нужна для заявления о готовом Telegram-only deployment; unit/HTTP tests её не заменяют.
5. SQL-реализацию проверяйте через postgres skill; для HTML — контекст вывода и экранирование; для внешних URLs — разрешённые схемы/назначения, redirects и доступ к внутренним адресам; для uploads — размер, тип и безопасный путь. Не проводите незапрошенное сканирование внешних сервисов.
6. Не выводите raw headers/cookies/env/logs. Для найденной проблемы покажите конкретный путь воздействия, минимальное исправление и targeted отрицательную проверку; не объявляйте всю систему безопасной по одному проходу.
