# Debugging Rizzoma

Симптом → слой → минимальный контекст → гипотеза → проверка → fix → targeted test.

- Зафиксируйте ожидаемое и наблюдаемое поведение. Определите слой: frontend, HTTP/API, DB, Docker или external service. Прочитайте ближайший caller/handler и относящийся тест, а не весь repository.
- Проверяйте одну объясняющую гипотезу наблюдаемым сигналом. После неуспеха меняйте гипотезу или условия; не повторяйте ту же команду без новых оснований.
- Подключайте backend-http/postgres/docker только когда локализованный дефект требует их правил. Внешние live-данные и исторический контекст нужны лишь при недостатке локальных фактов.
- Исправляйте причину в минимальной области, сохраняйте существующие контракты. Добавляйте regression-тест, если он проверяет реальное сломанное поведение, а не повторяет реализацию; не расширяйте тестовую инфраструктуру автоматически.
- Node tests: `node --test tests/<file>.test.mjs`; можно сузить через `--test-name-pattern` перед именем файла. Например, auth-проверки лежат в `tests/auth.test.mjs`; при отсутствии сборки contracts сначала соберите этот workspace.
- E2E: `npx playwright test tests/e2e/<file>.spec.mjs` только для затронутого пользовательского сценария с подходящими локальными/dev условиями. Browser capability подключайте для интерактивной диагностики UI/network/console, не для backend/SQL.
- Для TS/API по масштабу изменения используйте typecheck/build; полный suite нужен при широком влиянии или требовании проекта. Ошибку среды отличайте от ошибки приложения.
- В результате укажите причину, изменение, фактически выполненную проверку и оставшуюся неопределённость. Не сохраняйте временные debugging-наблюдения в Knowledge.
