# RIZZOMA — Telegram Mini App «дерево узлов»

> Ветка `feat/app`: базовое приложение без карты. Пользователи Mini App и бота
> регистрируются в PostgreSQL через единый TypeScript API. SQLite в этой ветке
> не используется и fallback на локальный файл отсутствует.

## Архитектура `feat/app`

```text
index.html + *.js        статический Telegram Mini App
assets/js/data/          модели клиента и persistence adapter
assets/brand/            внешние ресурсы бренда
        │
        ├── /api/v1/* ── apps/api (TypeScript, Express, PostgreSQL)
        │                  регистрация, сессии, health/readiness, миграции
        │
        └── /api/* ───── bot (Grammy + билеты/рефералы)
                           ├── подписанная регистрация в apps/api
                           └── PostgreSQL: счета, оплаты, баллы, beta
```

Основные границы:

- `apps/api/` — владелец регистрации и миграций PostgreSQL;
- `bot/storage.js` — транзакционные запросы бота к тому же PostgreSQL;
- `packages/contracts/` — общие схемы запросов и ответов;
- `db/migrations/001_identity.sql` — схема БД и начальная миграция в одном файле;
- `bot/` — Telegram-адаптер и существующие сценарии билетов;
- корневые `index.html`, `config.js`, `economy.js`, `engagement.js` — текущий
  frontend без изменения визуальной механики;
- `Dockerfile`, `docker-compose.yml`, `docker/` — воспроизводимый runtime.

`index.html` пока остаётся UI-entry point для Canvas и экранов. Модели и хранилище клиента
уже вынесены отдельно; разбиение Canvas/UI на компоненты остаётся самостоятельным этапом.

### Схема БД

Источником структуры приложения служат версионированные SQL-миграции.
[`db/migrations/001_identity.sql`](db/migrations/001_identity.sql) объединяет
начальную схему и её применение: таблицы `users`,
`participant_registrations`, `api_sessions`, связи, ограничения и индексы.
Отдельной ORM-схемы или дублирующего `schema.sql` нет.
`db/migrations/002_persistent_bot_state.sql` добавляет счета, подтверждённые
платежи, события активности и настройки беты, не изменяя первую миграцию.
При первом применении журнал платежей пуст: существующих реальных оплат для
переноса, по подтверждению владельца проекта, нет.
Служебную таблицу `schema_migrations` создаёт runner; он записывает контрольную
сумму SQL и повторно не применяет уже выполненную миграцию. После первого
развёртывания менять `001_identity.sql` нельзя — следующая правка БД должна
стать новой версионированной миграцией.

### Запуск через Docker

Используйте отдельные env-файлы из `docker/dev.env.example` и
`docker/prod.env.example`. Порядок настройки секретов, HTTPS, сборки одной
версии, проверки dev и выпуска prod описан в [docs/environments.md](docs/environments.md).
Не выводите полный `docker compose config`: он раскрывает секреты;
для проверки используйте `config --quiet`.

Web публикуется на loopback (dev 8082, prod 8080), API и PostgreSQL доступны
только внутри своего Compose project. Миграции выполняются при старте API.
Снаружи доступен HTTPS bootstrap; UI и API требуют серверную сессию.

### Локальная разработка без Docker

`npm run dev:web` запускает открытый UI fixture на `127.0.0.1:4321` для
визуальных тестов, без серверного gate. Не публикуйте этот сервер.
Для API скопируйте `apps/api/.env.example` в `apps/api/.env`, заполните
настройки dev и PostgreSQL, затем выполните `npm run db:migrate` и
`npm run dev:api`. Полная проверка входа требует HTTPS-прокси и nginx gate;
HTTP fixture не проверяет Secure cookie.

Приложение на один экран: генеративная сеть вокруг логотипа стала **радиальным деревом
прокачки**. Скиллы не нарисованы поверх сети — каждый сидит на реальной вершине её клина,
а глубина ветвления работает как кольцо прокачки. Билеты живут в bottom sheet и доступны
в один тап, «Свои» — соседняя вкладка.

**Сейчас проект в режиме беты.** Открыта только билетная часть дерева, остальное закрыто
туманом (см. [«Бета»](#бета-туман-войны)). Оплата идёт через платёжного провайдера, счёт
выставляет бот, узел засчитывается только после Telegram `successful_payment`.

При запуске на экране только фиолетовый «неактивный» знак. Касание разворачивает сеть
кольцо за кольцом, по ней прокатывается импульс готовности — и интерфейс проявляется.

Исходный UI поддерживает два режима; публичные dev/prod используют только первый:

- **как Mini App внутри Telegram** (основной сценарий) — разворачивается на весь экран,
  отдаёт оплату системной MainButton, закрывает модалки системной BackButton, добавляет
  тактильный отклик, синхронизирует узел и полученные скиллы через `CloudStorage`,
  читает диплинк `?startapp=КОД`;
- **как локальный fixture в браузере** — те же жесты мышью/пальцем, ссылки вида `?ref=КОД`,
  без хаптики и системных кнопок. Оплата в этом режиме — имитация, помеченная «тест».

Определение режима автоматическое (`WebApp.platform !== 'unknown'`), отдельной сборки нет.

## Экран и жесты

| Элемент | Поведение |
|---|---|
| Знак при запуске | единственное, что есть на экране; касание запускает развёртку сети (~2.3 с), после неё появляется интерфейс. До этого сцена на жесты не реагирует |
| Дерево | пан-зум внутри канвы (драг, колесо, пинч). Страница не скроллится нигде |
| Границы поля | считаются по каждой стороне отдельно: в сторону открытых ветвей поле едет столько, чтобы любой доступный узел доезжал до центра с запасом, а закрытые ветви границу не расширяют. Минимум везде один — знак-ядро не уходит с экрана. На дефолтном зуме ограничение не чувствуется, на приближении упор появляется только там, где туман |
| Кромка на overscroll | в сторону тумана — красная сигнальная штриховка и хаптика `rigid`; на обычном конце поля — тихая нить и `soft`: там не запрещено, там просто больше нечего смотреть. Отпустил — резинка вернула |
| Узел под туманом | не реагирует на удержание; тап показывает «вне беты» — текст и вид намеренно другие, чем у «нужно ещё N» |
| Подписи при зуме | раскладчик проверяет пересечения: что не помещается — плавно гаснет, что освободилось — проявляется. Наложений на поле нет ни на одном масштабе; пороги закрытых узлов показываются только крупнее ×0.92 |
| Тап по узлу | окно узла: имя скилла, награда, прогресс. Скромная анимация |
| Удержание ~1 c на доступном узле | активация скилла: кольцо заполняется, нарастает хаптика; отпустил раньше — отмена без изменения состояния |
| Активация завершена | прожиг ветви от ядра до узла, частицы, фиолетовый → токсично-зелёный, микро-тряска, `notificationOccurred('success')` |
| Заблокированный узел | на удержание не реагирует, тап показывает «ещё N узлов» |
| Кнопка «Билеты» | bottom sheet чекаута из любого состояния дерева |
| Вкладка «Свои» | список ветви и контактов от бота; сцена на паузе |
| Знак узла в баре | тап — активация узла / копирование ссылки, **пять тапов — бета-админка** (только для админов, см. ниже) |

Скиллы сгруппированы в три ветви (`BRANCHES`) по смыслу награды — это только группировка,
пороги и награды берутся из `TIERS` без изменений:

| Ветвь | Про что | Скиллы (порог в узлах) | В бете |
|---|---|---|---|
| I · **ВОЛЯ** | проходки и скидки на билеты | ПРОБИТИЕ (1), ПРОХОД (3), ОБХОД (10) | целиком |
| II · **ТЕЛО** | мерч, аксессуары, вещи, именной знак | КАПСУЛА (5), РЕЛИКТ (25), ТОТЕМ (100) | под туманом |
| III · **РАЗУМ** | VIP и пожизненные бонусы | ГЛУБИНА (15), КОНТУР (40), РЕЗИДЕНТ (60), ВЕЧНАЯ ВЕТВЬ (80) | только ГЛУБИНА |

Каждая ветвь — один луч сети (симметрия ×3, плюс зеркальные двойники как облако).
Хочешь переставить скилл в другую ветвь — правится массив `BRANCHES`, геометрия
пересчитается сама.

## 1. Публикация приложения

Нужен **HTTPS** — Telegram не открывает Mini App по http.

Для dev/prod используется nginx gate перед UI и API, с HTTPS-прокси на сервере.
Отдельный статический хостинг обходит проверку сессии и для этих контуров
не подходит. Шаблоны и приёмка — в [docs/environments.md](docs/environments.md).

## 2. Регистрация в BotFather

1. `/newbot` → имя и username → сохрани токен.
2. `/newapp` → выбери бота → название, описание, иконку **640×360**, **short name**
   (например `fest`) → на запрос Web App URL укажи HTTPS bootstrap своего контура.
3. Ссылка на приложение: `https://t.me/<бот>/<short name>`
   Реферальная: `https://t.me/<бот>/<short name>?startapp=КОД`

Дополнительно: `/setmenubutton` — чтобы приложение открывалось кнопкой рядом с полем ввода.

## 3. Настройка `config.js`

В Docker файл создаётся из `docker/config.js.template` и env своего контура.
Ниже пример настроек исходного UI для локальной разработки; QA в развёртывании
дополнительно требует `APP_ENV=dev`, `QA_ENABLED=true` и серверных прав.

```js
window.RIZZOMA_CONFIG = {
  bot: 'rizzoma_fest_bot',      // username без @
  app: 'fest',                  // short name из /newapp
  apiBase: 'https://api…',      // бэкенд: «Свои», счета, бета-админка
  crewDemo: false,
  prices: { std: 800, vip: 1600 },   // цена ОДНОЙ проходки, ₽. null → «уточняется»
  event: { line: 'VIDEO LOUNGE · 12.09 · СПб · 18+' },
  admins: [123456789],          // Telegram id админов беты (подсказка UI, решает сервер)
  panel:    RZ_ADMIN_LINK,      // ставится сама: true только по ссылке ?mode=admin
  qaButton: RZ_ADMIN_LINK
};
```

Как только заполнены `bot` и `app`, кнопка «Поделиться» отдаёт ссылку
`t.me/бот/апп?startapp=КОД` вместо `?ref=КОД` — то есть открывает приложение, а не браузер.

Цены здесь дублируют серверные `PRICE_STD`/`PRICE_VIP`: клиент показывает сумму, но
считает её заново сервер, и в счёт попадает именно серверное число.

## Секреты

`BOT_TOKEN` даёт полный контроль над ботом — в репозиторий он не попадает никогда,
даже в приватный. Место токена — переменные окружения хостинга бэкенда;
локально он лежит в `bot/.env`, который закрыт `.gitignore`.
В репозитории есть только `bot/.env.example` с плейсхолдерами.

Если токен всё-таки где-то засветился — `/revoke` у @BotFather, затем `/token` за новым.

В статике (`index.html`, `config.js`) секретов нет и быть не должно.

## 4. Бэкенд (нужен для оплаты, «Своих» и бета-админки)

Запускайте сервисы с отдельным env-файлом по [инструкции dev/prod](docs/environments.md).
Для отдельного локального запуска бота сначала поднимите PostgreSQL,
примените `npm run db:migrate` и запустите API регистрации.

```bash
cd bot
cp .env.example .env      # также DATABASE_URL и REGISTRATION_API_BASE
npm install
npm start
```

Затем пропиши в `config.js` → `apiBase: 'https://адрес-бэкенда'`.

Переменные окружения:

| Переменная | Зачем |
|---|---|
| `BOT_TOKEN` | токен бота из @BotFather |
| `DATABASE_URL` | PostgreSQL с применёнными миграциями `001` и `002` |
| `REGISTRATION_API_BASE` | внутренний адрес API регистрации |
| `APP_URL` | HTTPS-адрес статики |
| `PROVIDER_TOKEN` | токен платёжного провайдера (см. §5). Пока в нём `TEST` — деньги не списываются |
| `CURRENCY`, `PRICE_STD`, `PRICE_VIP` | валюта и цена одной проходки. Пусто — счёт не выставляется |
| `ADMIN_TG_IDS` | id админов беты через запятую. Пусто — бета-админка не откроется никому |
| `BETA_OPEN` | список открытых узлов беты контура (`0,1,3,4`). Обязателен для dev и prod, проверяется при запуске: неверный или пустой останавливает бота. Меняется деплоем — см. [`docs/beta-config.md`](docs/beta-config.md) |
| `CORS_ORIGIN` | домен статики |

## Бета: туман войны

Бета проверяет один сценарий целиком: **пригласил → друг оплатил → тебе узел → узел
превращается в скидку или бесплатный вход**. Всё, что к этому сценарию не относится,
закрыто туманом.

| Открыто | Под туманом |
|---|---|
| ПРОБИТИЕ (1) · ПРОХОД (3) · ОБХОД (10) — вся ветвь ВОЛЯ | КАПСУЛА (5) · РЕЛИКТ (25) · ТОТЕМ (100) — мерч |
| ГЛУБИНА (15) — единственная VIP-привилегия | КОНТУР (40) · РЕЗИДЕНТ (60) · ВЕЧНАЯ ВЕТВЬ (80) |

Узлы под туманом **не вырезаны из сцены**: геометрия, звенья и сигилы на месте, просто
накрыты мглой — карта видна целиком, неразведанная часть читается как «ещё не открыто».

Два «закрыто» намеренно выглядят и читаются по-разному:

| Состояние | Что показывает | Текст |
|---|---|---|
| не хватает приглашённых | прогресс до порога, кнопка «Позвать своих» | «Ещё N узлов» |
| вне беты | пунктирный блок со списком того, что открыто | «Не участвует в бете» |

Набор открытых узлов — настройка сервера: `BETA_OPEN` в env контура (dev и prod свои),
модуль `bot/beta-config.js` проверяет его при запуске, список приходит клиенту в
`/api/state`. Меняется он вместе с релизом: правка env и пересоздание бота. До ответа
сервера приложение показывает последний полученный список (`rizzoma_beta`), а без него —
`BETA_OPEN` из `economy.js`. Публичный `config.js` туман не задаёт.

## 5. Оплата

Билет на реальное событие — **физическая услуга**, поэтому Stars не обязательны и
подключается обычный платёжный провайдер
([Bot Payments API](https://core.telegram.org/bots/payments);
Stars нужны только для цифровых товаров —
[payments-stars](https://core.telegram.org/bots/payments-stars)).

### Как подключить

1. Оформи статус самозанятого или ИП — провайдер без него договор не заключит.
2. Зарегистрируйся у провайдера (см. таблицу ниже) и получи доступ к личному кабинету.
3. @BotFather → `/mybots` → бот → **Payments** → выбрать провайдера → пройти форму →
   вернуться в BotFather за **Provider token**.
4. Положи токен в `PROVIDER_TOKEN` на хостинге бэкенда (не в репозиторий, не в `config.js`).
5. Для dev задайте `PAYMENT_MODE=test` с токеном `:TEST:`; для prod — `live`
   с токеном `:LIVE:` после проверки на dev. По умолчанию `disabled`.

### Чем платить при обороте до ~100 000 ₽/мес

Комиссии меняются — перепроверь в личном кабинете перед подключением.

| Провайдер | Комиссия (ориентир) | Почему подходит | Ссылки |
|---|---|---|---|
| **ЮKassa** — основной | карты от 2,8%, СБП от 0,4% | нативная интеграция с BotFather, без абонплаты, онлайн-подключение для самозанятых | [yookassa.ru](https://yookassa.ru/) · [для самозанятых](https://yookassa.ru/platezhi-dlya-samozanyatyh/) · [тарифы](https://yookassa.ru/fees/) |
| **Robokassa** — запасной | без абонплаты, чеки в тарифе | подключение через `@RobokassaShopBot`, быстрый онбординг; полезен, если основной провайдер попросит доп. проверку по категории «ночное мероприятие 18+» | [robokassa.com](https://robokassa.com/solutions/business/samozanyatye/) |
| CloudPayments / Prodamus | индивидуально | избыточны для этого оборота; пригодятся, когда появятся подписки и рассрочка | [cloudpayments.ru](https://cloudpayments.ru/) |

На таком обороте разница в процентах меньше, чем разница в возне с подключением:
подключай СБП первым способом оплаты (самая низкая комиссия), карты — вторым.

### Как устроено в коде

```
приложение            бэкенд                         Telegram
   │  /api/invoice ──────▶ считает сумму сам
   │                       createInvoiceLink ──────▶ окно оплаты
   │  ◀── link ──────────                            │
   │  WebApp.openInvoice(link) ──────────────────────▶
   │                       ◀── pre_checkout_query ───
   │                       сверяет сумму заново
   │                       ◀── successful_payment ───
   │                       здесь и только здесь:
   │                       paid = true, узел засчитан
```

Клиент не участвует в начислении: он присылает только состав и класс билета, а сумму,
скидку за узлы и VIP без наценки считает сервер по `economy.js`. Подделать цену подменой
запроса нельзя — в счёт уйдёт серверное число, а `pre_checkout_query` сверит его ещё раз.

Вне Telegram (или пока `apiBase` пуст) остаётся прежняя клиентская имитация с валидацией
Луна и тестовыми картами — она помечена «тест» прямо в форме.

## 6. Два аккаунта: как тестировать

Продовый бот не трогаем — для беты заводится отдельный.

| Что | Аккаунт №1 (админ) | Аккаунт №2 (тестер) |
|---|---|---|
| Роль | заводит ботов в BotFather, держит бета-админку | обычный участник теста |
| Бот | `@rizzoma_beta_bot` (отдельный токен, отдельный `APP_URL`) | тот же бета-бот |
| Доступ к панели | id в `ADMIN_TG_IDS` (сервер) и в `config.js → admins` (UI) | нигде — панель не откроется |
| Сценарий | генерирует ссылку `?startapp=КОД`, смотрит воронку | заходит по ссылке, платит sandbox-платежом |

Сквозная проверка занимает пять минут:

1. Аккаунт №1 открывает приложение, копирует свою ссылку.
2. Аккаунт №2 открывает ссылку, покупает билет (`PROVIDER_TOKEN` с `TEST`).
3. У аккаунта №1 в баре растёт счётчик узлов, открывается ПРОБИТИЕ, во вкладке «Свои»
   появляется тестер, в бета-админке — строка в воронке и платёж в журнале.

Почему так: реферальная атрибуция и платёж — единственные места, где нужны два разных
Telegram-аккаунта; всё остальное проверяется автотестами.

## Баллы за активность в канале

Вторая, независимая от дерева узлов система: дерево считает рефералов, эта — действия
в [t.me/rizzoma26](https://t.me/rizzoma26). Общего у них только пользователь.

| Действие | Баллы | Считается |
|---|---|---|
| Подписка на канал | 5 | один раз на человека: отписался и вернулся — второй раз не платят |
| Реакция на пост | 2 | один раз на пару «человек + пост»; смена эмодзи и снятие реакции ничего не меняют |
| Буст канала | 15 | один раз на буст; снятие буста **списывает** ровно начисленное за него |
| Комментарий | 3 | только если к каналу привязана группа обсуждений; не больше 5 засчитанных в сутки |

Правки — в [`engagement.js`](engagement.js), массив `RULES`. Там же вся арифметика:
дедуп, потолок и откат — чистыми функциями, поэтому они покрыты юнит-тестами, а бот
только хранит и вызывает.

### Что Telegram отдаёт, а что нет

Bot API присылает боту `chat_member`, `message_reaction`, `chat_boost` **только если
бот — администратор канала** и эти типы явно перечислены в `allowed_updates` при старте
(это сделано, константа `ALLOWED_UPDATES` в `bot/bot.js`). Без прав администратора не
придёт ничего, и это не чинится кодом.

Просмотры постов, пересылки, скриншоты и любая история **до** того, как бота сделали
админом, недоступны никому через Bot API — в системе их нет и не будет.

Анонимная реакция «от лица канала» приходит без пользователя — привязать её не к кому,
такие события пропускаются.

### Настройка

1. Добавить бота администратором в канал.
2. Узнать числовой id канала и положить в `CHANNEL_ID` (см. `bot/.env.example`).
   Пока переменная пуста, бот не начисляет ничего — это защита от раздачи баллов
   в чужих чатах, куда его могут позвать.
3. Если появится группа обсуждений — её id в `DISCUSSION_ID`, тогда заработает правило
   «комментарий». Привязывается группа вручную в Telegram (Канал → Обсуждение),
   Bot API этого не умеет.

### Где хранятся баллы

Считает их бот (реакции и подписки прилетают ему, а не в браузер). В Docker
баллы хранятся в PostgreSQL; браузер оставляет только кэш:

| Где | Что |
|---|---|
| PostgreSQL | события активности с дедупликацией, оплаченные счета, настройки беты и профиль пользователя |
| `localStorage` клиента | ключ `rizzoma_engagement` — кэш последнего ответа `/api/engagement` |

Ключ намеренно **не** в `CLOUD_KEYS`: баллы остаются на устройстве, как `rizzoma_beta`,
а не синхронизируются через `CloudStorage`, как узел и полученные скиллы. Если
пользователь открывает другое устройство, актуальные баллы заново приходят из
PostgreSQL через `/api/engagement`; локальный ключ — только офлайн-кэш.

Видно баллы во вкладке «Свои», блоком «Активность в канале». Пустое состояние всегда
объясняет причину: «бэкенд не подключён», «бот ещё не следит за каналом» и «ноль
баллов» — разные сообщения, а не один пустой блок.

## Вкладка «Свои» — что здесь возможно, а что нет

**Невозможно:** получить адресную книгу пользователя. У Telegram нет такого метода
ни для Mini App, ни для Bot API. `requestContact` тоже не решает задачу — он отдаёт
серверу *твой* номер, а не список твоих знакомых.

**Возможно и реализовано:** граф из реферальных переходов, который бот записывает сам.

| Источник | Когда доступен |
|---|---|
| твоя ветвь — кто пришёл по твоей ссылке | всегда, даже без бэкенда (локальные данные) |
| кто позвал тебя | после привязки аккаунта через бота |
| соседи по ветви — приглашённые тем же человеком | после привязки аккаунта |
| демо-контакты с пометкой `демо` | пока `apiBase` не задан |

Привязка: кнопка «Привязать через бота» открывает `t.me/<бот>?start=link_КОД`,
бот запоминает пару «аккаунт ↔ узел».

### Контракт API

Все запросы — `POST`, тело JSON, обязательное поле `initData`
(строка `Telegram.WebApp.initData`; сервер проверяет её HMAC по схеме `WebAppData`,
требует ровно 64 hex-символа в `hash` и отвергает всё старше суток).

| Эндпоинт | Тело | Ответ |
|---|---|---|
| `/api/visit` | `{initData, ref}` | `{ok:true}` — фиксирует, по чьей ссылке открыто приложение |
| `/api/state` | `{initData}` | `{code, paid, refs, invitedBy, betaOpen, prices, revoked}` — источник правды для приложения |
| `/api/invoice` | `{initData, cls, size, ref}` | `{link, amount, currency}` — ссылка на счёт; сумму считает сервер |
| `/api/friends` | `{initData}` | `{linked, friends:[…]}` |
| `/api/engagement` | `{initData}` | `{points, events:[…], tracking, discussion}` — свои баллы за канал; `tracking:'off'` значит, что `CHANNEL_ID` не задан |
| `/api/purchase` | `{initData}` | `{ok:true, note}` — оставлен для совместимости, оплату больше не засчитывает |
| `/api/admin/overview` | `{initData}` | `{betaOpen, testers:[…], payments:[…], totals}` — **403** вне `ADMIN_TG_IDS` |
| `/api/admin/tester` | `{initData, id, action}` | `{ok:true, revoked}` — отзыв и возврат доступа |

Элемент `friends[]`:

```json
{ "id":"123", "name":"Ника В.", "username":"nika_void",
  "photo":"https://…", "status":"paid", "tier":2 }
```

`status`: `paid` — допуск оплачен · `node` — в сети, но без оплаты · `none` — можно позвать.

`/api/visit` вызывает само мини-приложение: параметр `startapp` до бота не долетает,
он приходит только в `initDataUnsafe.start_param`.

Оплату не подтверждает ни один эндпоинт: `paid` и начисление узла ставит только обработчик
`successful_payment` внутри бота.

## Хранилище

| Ключ | Содержимое |
|---|---|
| `rizzoma_mock_db` | `{users:{…}, buyers:{…}, profiles:{…}, claims:{КОД:[индексы скиллов]}}` |
| `rizzoma_me` | код текущего узла |
| `rizzoma_attribution` | `{code, ts}`, TTL 30 дней |
| `rizzoma_claims` | компактное зеркало полученных скиллов: `{code, list:[…]}` |
| `rizzoma_beta` | какие узлы открыты (туман). Перекрывается ответом `/api/state` |

`claims` — аддитивное расширение прежней схемы; отдельный ключ `rizzoma_claims` нужен
потому, что лимит CloudStorage — 4096 символов на ключ, и полный дамп БД туда со временем
перестаёт помещаться, а список скиллов помещается всегда.

Как только задан `apiBase`, `/api/state` приносит код, статус оплаты,
число оплаченных приглашённых и настройки беты из PostgreSQL. `localStorage`
остаётся кэшем на случай офлайна; повторная доставка платежа Telegram не
начисляет его повторно.

## Что заменить перед боевым запуском

| Сейчас | В проде |
|---|---|
| профиль, подтверждённые платежи и engagement в PostgreSQL, туман — `BETA_OPEN` контура | проверить работу миграций и сценария оплаты на живом PostgreSQL и Telegram sandbox |
| `PROVIDER_TOKEN` с `TEST` | боевой токен провайдера (деньги начнут списываться) |
| `QA_ENABLED=true` только в dev | `QA_ENABLED=false`; сервер prod запрещает QA |
| цены в двух местах (`config.js` и env бэкенда) | одно место: клиент берёт цены из `/api/state` |

Локальный UI fixture без бэкенда работает на `localStorage` — это демо-уровень: данные
правятся из консоли браузера, на них нельзя вешать реальные награды.

## Две ссылки: тестер и админ

В dev при `QA_ENABLED=true` одна сборка имеет два вида интерфейса по параметру адреса:

| Кому | Ссылка | Что видит |
|---|---|---|
| тестеру | `…/rizzoma/` | только приложение: дерево, билеты, «Свои». Панели нет ни по `?admin=1`, ни по пяти тапам, ни кнопкой |
| себе | `…/rizzoma/?mode=admin` | то же плюс бета-админка и кнопка `QA` в баре |

Разделение делает `config.js`: он проверяет `mode=admin` и выставляет `panel`/`qaButton`.
**Это разделение интерфейсов, а не защита** — адрес видно в коде страницы. Настоящие
права даёт только бэкенд: живые данные (воронка и платежи) приходят
после проверки сессии, `DEV_ALLOWED_TG_IDS` и `ADMIN_TG_IDS` поверх подписанной
`initData`, и ссылка на это не влияет. На prod QA API закрыт.

Внутри Telegram ссылка задаётся в BotFather, поэтому админская версия — это отдельное
мини-приложение у того же бота: `/newapp` → short name, например `admin`, Web App URL
с `?mode=admin`. Тестеры получают обычный short name.

## Бета-админка

Открывается только в админской сборке. Три входа:

1. **Кнопка `QA` в баре** — видна, если `qaButton: true` **и** твой id есть в `config.js → admins`.
2. `?admin=1` (синоним `?devpanel=1`).
3. **Пять тапов по знаку узла в баре.**

Внутри Telegram id не из `admins` не откроет панель ни одним из трёх способов — вместо
неё появится «Раздел недоступен». В браузере по админской ссылке панель открыта: там
она правит только `localStorage` этой вкладки и нужна для приёмки и автотестов.

Живые данные (воронка тестеров и журнал платежей) приходят только после
того, как бэкенд подтвердил доступ по `ADMIN_TG_IDS` поверх проверенной `initData`.
Список в `config.js` — подсказка интерфейса, доступа к данным он не даёт.

| Раздел | Что делает |
|---|---|
| **Туман** | только чтение: какие узлы открыты в бете. Список задаёт `BETA_OPEN` контура, меняется деплоем |
| **Тестеры · воронка** | кто зашёл, кто оплатил, сколько узлов, отзыв и возврат доступа |
| **Платежи теста** | журнал: счёт выставлен / оплачен, сумма, состав и класс билета |
| Состояние узла | произвольное число рефералов, `+1` / `+5`, вход под чужим узлом, сброс атрибуции |
| Скиллы | `open` / `claim` превью анимаций **без изменения состояния**, точечная выдача и сброс |
| Переключатели | «все скиллы разлочены» (туман при этом не снимается), reduce motion |
| Сырые данные | экспорт/импорт JSON, «Выгрузить лог» — состояние + журнал событий одним куском |

`?reduce=1` — статичный режим (эквивалент `prefers-reduced-motion: reduce`): дерево,
активация скиллов и покупка билета работают, победная анимация упрощается до смены состояния.

Тестовые карты имитации (вне Telegram): `4242 4242 4242 4242` — успех,
`4000 0000 0000 0002` — отказ.

## Автотесты

```bash
npm install
npm install --prefix bot   # интеграционные тесты импортируют настоящий bot/bot.js
npm test                   # экономика, баллы за канал, приём Telegram-апдейтов
npm run test:e2e           # Playwright: туман, кромка, чекаут, админка, активность
```

Без зависимостей бэкенда `tests/engagement.bot.test.mjs` не запустится — он поднимает
настоящий `bot.js`, которому нужны `grammy` и `express`.

| Файл | Что проверяет |
|---|---|
| `tests/economy.test.mjs` | цены, лестница скиллов, состав беты |
| `tests/engagement.test.mjs` | начисление баллов, дедуп, суточный потолок, откат буста |
| `tests/engagement.bot.test.mjs` | приём настоящих Telegram-апдейтов: фильтр чата, отсев ботов, анонимные реакции, `/api/engagement`, `allowed_updates` |
| `tests/beta-config.test.mjs` | строгий разбор `BETA_OPEN`: диапазон, повторы, пустые элементы, текст ошибки без чужих значений |
| `tests/beta-api.bot.test.mjs` | `/api/state` отдаёт список контура, записи беты через API нет |
| `tests/e2e/beta.spec.mjs` | туман, кромка поля, чекаут, доступ к бета-админке |
| `tests/e2e/engagement.spec.mjs` | показ баллов, пустые состояния, локальное хранение |

Юнит-тесты гоняют `economy.js` и `engagement.js` — те самые файлы, по которым считают
приложение и бэкенд, без моков и без сборки. Интеграционные тесты импортируют настоящий
`bot/bot.js` и скармливают ему синтетические `Update` через `bot.handleUpdate()`: ни сети,
ни токена, ни Telegram для этого не нужно (сеть бот поднимает только при прямом запуске
файла, не при импорте). E2E поднимают статику (`tests/serve.mjs`) и водят
приложение в chromium; Telegram-SDK и `config.js` подменяются на уровне сети, поэтому
проверяется и поведение внутри Telegram — включая то, что тестер не открывает админку.

Узлы живут на канве и не имеют DOM-элементов, поэтому e2e берут их координаты через
`window.__RZ` — объект появляется только при `?e2e=1` и в обычном запуске не существует.

CI (`.github/workflows/ci.yml`) гоняет оба набора на каждый push и отдельно проверяет,
что в репозиторий не уехал `.env` или токен бота.

## Экономика

Всё в [`economy.js`](economy.js): `TIERS` — лестница узлов (`n` — порог, `label` — награда,
`skill`/`line` — подача), `BRANCHES` — разбивка по ветвям, `BETA_OPEN` — что открыто в бете,
`TICKET_CLASS` / `TICKET_SIZE` — класс и состав билета, `comboPrice()` — расчёт суммы.

Цена: `база класса × состав`, где скиллы дерева закрывают **только свою** проходку —
−20% с одного узла, бесплатно с трёх, VIP без наценки с ГЛУБИНЫ. Соседние места в парном
и тройном билете идут по полной цене, иначе один узел обнулял бы сразу три входа.
