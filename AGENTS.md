# Rizzoma

- Текущую ветку и `git status` проверяйте перед правками; сохраняйте чужие изменения. Удалённый Git — по отдельному запросу. Личный проект: корпоративные Jira/Confluence/TestOps не используются; глобальные настройки не меняются.
- Базовый контур — PostgreSQL без FogMap/SQLite. Frontend: `index.html`, `registration.js`; API: `apps/api`; bot: `bot`; контракты: `packages`; SQL: `db/migrations`.
- Инварианты: применённые миграции неизменны; dev/prod не делят состояние и секреты; защищённый UI/API требует серверную Telegram-авторизацию и сессию, dev — allowlist. QA/тестовые платежи — только dev.
- Не выводите значения env, credentials, токены, initData и платёжные данные; диагностируйте только имена и `<set>`/`<unset>`.
- Контекст: один подходящий skill → нужные файлы → targeted проверка; второй skill только по необходимости. Не загружайте весь каталог skills/docs и не запускайте Superpowers автоматически.

| Задача | Skill в `.agents/skills/` |
|---|---|
| Новые компоненты, архитектура, data flow | `system-design` |
| HTTP/API, endpoints, fetch, интеграции | `backend-http` |
| SQL, схема, миграции, запросы | `postgres` |
| Контейнеры, Compose, deployment | `docker` |
| Баг, сбой теста, диагностика | `testing-debugging` |
| Auth, доступ, недоверенные данные, секреты | `security-review` |

Для Rizzoma Knowledge-поиск **не является обязательным стартом**: это проектное исключение из общего правила. Текущее поведение проверяйте по коду; исторические требования, решения и provenance ищите через существующий `/Users/gruber/.agents/skills/wiki` только по необходимости. Расхождения маркируйте **CONTRADICTION**: наблюдаемое / документированное / предлагаемое. При явно разрешённой записи используйте существующий transaction workflow, не создавайте вторую wiki.

Команды из корня: `npm run dev:api`, `npm run dev:web`; проверки — `node --test tests/<file>.test.mjs`, `npm run typecheck`, `npm run build`, `npx playwright test tests/e2e/<file>.spec.mjs`. Выбирайте по изменённому слою; полный `npm test` — при широком влиянии. Для docs/config проверяйте сами файлы. В результате укажите проверенное и ограничения.

Browser, live MCP и актуальная документация — по задаче: [подключение возможностей](docs/agent-workflows.md#возможности). Не объявляйте deployment готовым по одним шаблонам.

## Передача контекста в Git

- Перед изменениями проверьте `git status`; перед передачей ветки выполните `npm run handoff`. Команда обновляет `docs/handoffs/branch-context.md` сведениями о ветке и изменённых путях; содержимое исходников и env-файлов она не читает.
- Пакуйте вместе исходный код, применимые `.agents/skills/`, требования, решения и актуальные результаты проверок. Сверяйтесь с [индексом документации](docs/index.md); исторические промпты и проект модуля «Мир» не являются автоматически действующими требованиями.
- Не переносите в Git `.env`, ключи, токены, `.idea/`, `.superpowers/`, резервные `.bak`, локальные настройки инструментов и `docs/codex-*` audit-артефакты с host-specific путями. Генератор показывает пропущенные локальные материалы только количеством.
- Генератор не делает `git add`, commit, push и не выполняет проверки runtime. После него вручную проверьте список файлов, `git diff`, staged diff и секреты; отправляйте только намеренно включённые изменения.
