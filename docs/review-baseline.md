# Проверка базового приложения

Срез кода: `feat/app`, 2026-09-28. Область: Mini App, API авторизации, Bot API, PostgreSQL,
клиентское хранение и статические ресурсы. Результат относится к коду; реальные Telegram
клиенты, сервер с PostgreSQL и платёжный sandbox требуют отдельного runtime-прогона.

## Исправлено в этой правке

1. **Повторный вход создавал лишние сессии.** Bootstrap выдавал новую сессию при каждом открытии,
   затем `registration.js` ещё раз делал POST при загрузке UI. Оба этапа теперь проверяют
   `/api/v1/session`, сверяют `/api/v1/me` с Telegram identity и переиспользуют только
   совпадающую сессию; иначе выполняют регистрацию.
2. **Модель клиента, адаптер хранения и интерфейс были смешаны.** JSON-модели лежат в
   `assets/js/data/entities.js`, localStorage/CloudStorage и идемпотентные операции — в
   `assets/js/data/client-state-repository.js`, UI делегирует им загрузку и сохранение.
3. **Claim повторно мог менять кэш через прямую мутацию массива.** `grantClaim()` теперь
   проверяет индекс, сортирует список и сохраняет только первое добавление.
4. **Один контур логотипа хранился в двух копиях — SVG-файле и инлайн-`symbol`.** Обе страницы
   используют `assets/brand/logo.svg`; Canvas получает путь из того же файла.
5. **Domain interfaces были рядом с SQL-репозиторием.** `UserRecord` и `RegistrationRecord`
   вынесены в `apps/api/src/auth/auth.models.ts`; SQL row-интерфейсы остались у репозитория.

## Проверяемые гарантии повторного выполнения

- Миграционный runner использует PostgreSQL advisory lock и checksum.
- Telegram identity уникальна по `users.telegram_user_id`; регистрация выполняет upsert.
- Telegram charge ID уникален; повторный receipt не добавляет оплату.
- Awards активности используют уникальный активный `dedup_key`.
- Повторная регистрация страницы при действующей cookie теперь не создаёт новую сессию.
- Повторный клиентский skill claim/merge и запись `betaOpen` сохраняют стабильное состояние.

Повторный прямой POST регистрации без действующей cookie по контракту остаётся новым входом
и может выдать новую сессию. Сборка/тесты проверяют кодовые инварианты, но не проводят
конкурентный PostgreSQL-тест в этой задаче.

## Остаточные риски

- Клиентские `claims`, demo-профили и attribution редактируются владельцем браузера. Не выдавать
  на их основании ценную награду; при появлении такого сценария нужен серверный claim endpoint
  с ограничением в БД.
- `localStorage` и Telegram CloudStorage не образуют атомарную многоклиентскую реплику. Текущая
  merge-логика удобна для интерфейса, но не подходит для конкурентных изменений.
- При сетевой ошибке регистрации часть UI продолжает показывать локальный кэш; для эксплуатации
  нужно добавить видимое состояние ошибки и измеримую телеметрию без персональных данных.
- Canvas-сцена всё ещё живёт в большом `index.html`; отдельные debounce/frame metrics не добавлены.
- Bot обновления обрабатываются через long polling. Повтор Telegram payment защищён receipt
  constraint, но гарантии доставки всех типов update при рестарте отдельно не подтверждены.
- Истечение и отзыв сессии проверяются API; очистка истёкших строк из `api_sessions` не входит
  в текущий фоновый runtime.

## Проверки

Фактически выполнены после изменения:

- `npm test` — все 58 unit/integration tests прошли; запуск требовал loopback-доступа для
  тестового HTTP-сервера.
- `node --test tests/bootstrap.test.mjs tests/client-state.test.mjs tests/registration.test.mjs`
  — точечные проверки повторного входа, referral capture, claim, merge и beta state.
- `npm run typecheck` — shared contracts и TypeScript API.
- `npm run build` — contracts и TypeScript API собираются.
- `docker compose --env-file docker/dev.env.example config --quiet` и аналогичная prod-команда
  — конфигурации разбираются с временными URL-заглушками; сервисы не запускались.
- `node --check` для новых browser modules, bootstrap/registration, parse inline JS обеих страниц,
  проверка структуры SVG и `git diff --check`.

Playwright E2E запущен, но не стартовал: установленный пакет не находит локальный
`chromium_headless_shell`. Поэтому экран и внешняя SVG-ссылка в реальном браузере этой
проверкой не подтверждены; браузер не устанавливался и внешние сервисы не вызывались.

Внешний бот, PostgreSQL,
TLS-cookie на реальном домене и провайдер платежей этой проверкой не подтверждаются.
