# Бета: конфигурация контура вместо `beta_settings`

Журнал переноса настройки беты из таблицы `beta_settings` в серверный модуль
(скиллы `.agents/skills/beta-config-00…05`). Вынос статических данных сцены (`06`) —
в [`assets.md`](assets.md).

## 00. Решение

**Вариант B — перенос.** Бета меняется вместе с релизом, а не через админку. Решение принял
владелец 2026-09-29 в ответ на вопрос скилла 00.

Почему это продуктовое изменение, а не чистка БД: раньше dev-админ (при `QA_ENABLED=true`)
переключал туман в панели без деплоя. Теперь список меняется правкой `BETA_OPEN` в env
контура и пересозданием бота. В prod штатного пути изменения не было и раньше: `QA_ENABLED`
там запрещён, менять можно было только прямым SQL.

Подрешения (значения по умолчанию из скилла 00):

| Вопрос | Решение |
|---|---|
| Откуда значение контура | переменная `BETA_OPEN` в env-файле контура |
| Способ менять бету в dev без деплоя | нет; пересоздание бота с новым env |
| Дубликаты, пустой элемент, пустой список | ошибка запуска, не нормализация |
| Поставка | две: сначала код без обращений к `beta_settings`, затем миграция `003` |
| Админ-панель | переключатель убран, список открытых узлов показывается только для чтения |

## 02. Эффективные значения dev и prod

Эффективное значение — строка `beta_settings` (id = 1): её отдавал `/api/state`. Env и
`economy.js` использовались только при первом создании строки.

| Контур | Как получено | Таблица есть | Значение в БД | Менялось админом | `updated_at` | `BETA_OPEN` в env | По умолчанию | Эффективное | Дата |
|---|---|---|---|---|---|---|---|---|---|
| dev | **выведено, не измерено** | не проверено | не прочитано | не проверено | — | пусто в `docker/dev.env.example` | `0,1,3,4` | `0,1,3,4` | 2026-09-29 |
| prod | **выведено, не измерено** | не проверено | не прочитано | не проверено | — | пусто в `docker/prod.env.example` | `0,1,3,4` | `0,1,3,4` | 2026-09-29 |

Почему не измерено: у сессии, выполнявшей перенос, нет доступа к серверу, env-файлам
`/etc/rizzoma/*.env` и БД контуров, а по [`environments.md`](environments.md) реальное
развёртывание ещё не выполнено. Выведенное значение записано в шаблоны
`docker/dev.env.example`, `docker/prod.env.example` и `.env.example`.

**CONTRADICTION** — наблюдаемое / документированное / предлагаемое: наблюдать значения
контуров не удалось; шаблоны раньше оставляли `BETA_OPEN` пустым; предлагается перед
выкладкой кода из этой ветки снять настоящее значение каждого контура командой ниже и
записать в env контура именно его. Особенно важно для dev: если админ менял туман в панели,
значение в БД отличается от `0,1,3,4`.

```bash
tools/beta-settings-capture.sh /etc/rizzoma/dev.env
tools/beta-settings-capture.sh /etc/rizzoma/prod.env   # только с согласия владельца
```

Скрипт только читает: SQL идёт в read-only транзакции (`tools/beta-settings-capture.sql`), env
не меняется. Печатает применённые миграции, строку `beta_settings` (значение, «менялось
админом: да/нет» без id администратора, `updated_at`), статус переменных и готовую строку
`BETA_OPEN=…`. Расхождения помечает `CONTRADICTION`:

- в БД порядок или повторы отличаются от нормализованного списка — модуль отдаёт индексы по
  возрастанию без повторов;
- env расходится с БД — действует значение БД, его и сохранить.

Если в БД пустой список, скрипт завершается с кодом 3: клиенты такой ответ игнорировали и
держали свой кэш, поэтому значение для контура выбирает владелец. Env-файл правится вручную
после подтверждения владельца: сначала `cp -p` на резервную копию, затем
`docker compose --env-file … config --quiet`. Контейнеры до выкладки кода не пересоздавать.

Скрипт проверен на одноразовом PostgreSQL 16 с миграциями `001`–`002` (строка есть, строки
нет, пустой список, env расходится с БД) через заглушку `docker compose`; на живых контурах
не запускался.

## 01 и 03. Источник истины — конфигурация контура

| Что | Где |
|---|---|
| Список открытых узлов | `BETA_OPEN` в env контура → `bot/beta-config.js` (`loadBetaConfig`) |
| Проверка | при запуске бота, до подключения к БД: нецелое, вне `0…N-1` (`N = ECON.TIERS.length`), пустой элемент, повтор, пустой список — выход с кодом 1 и сообщением `BETA_OPEN: …`; в `docker compose config` пустое значение — ошибка подстановки |
| Чтение | `/api/state` и `/api/admin/overview` отдают `betaOpen` модуля: индексы по возрастанию |
| Запись | нет: `POST /api/admin/beta` удалён (теперь 404), `PostgresBotStore.beta()`/`setBeta()` удалены, бот не создаёт и не читает строку `beta_settings` |
| Клиент | переключатель тумана в панели удалён; секция «Туман» показывает список только для чтения. `betaOpen` в публичном `config.js` больше не читается. До ответа `/api/state` виден последний кэш `rizzoma_beta`, без него — `economy.js` |
| Права | `auth`, `adminAuth`, `QA_ENABLED`, `ADMIN_TG_IDS`, `DEV_ALLOWED_TG_IDS` не менялись |

Первый кадр. Если значение контура отличается от кэша устройства (или от `economy.js` на
первом запуске), до ответа `/api/state` туман кратко показывает прежний список, затем
перерисовывается. Это поведение было и раньше, e2e фиксирует его на задержке ответа
1,5 с (`tests/e2e/beta.spec.mjs`, «первый кадр до ответа сервера»). Отдельно не исправлялось.

## 04. Миграция `003_drop_beta_settings.sql`

`db/migrations/003_drop_beta_settings.sql` — одна строка `DROP TABLE beta_settings;`, без
`IF EXISTS`: таблицу создаёт `002`, и её отсутствие означало бы дрейф схемы. Применённая
`002_persistent_bot_state.sql` не менялась (sha256 `86c306ec…63873565`, фиксирует
`tests/beta-migration.db.test.mjs` и в CI).

Проверено на одноразовом PostgreSQL 16 настоящим раннером `apps/api/src/db/migrate.ts`
(`RIZZOMA_SCRATCH_DATABASE_URL=… node --test tests/beta-migration.db.test.mjs`; без переменной
тест БД пропускается, адрес принимается только локальный):

| Случай | Результат |
|---|---|
| Чистая БД | применены `001`, `002`, `003`; `beta_settings` нет; в `schema_migrations` три записи |
| Контур с применёнными `001`–`002` (та же схема журнала и те же суммы, что пишет раннер) и строкой `beta_settings` | применена только `003`; таблица удалена; сумма `002` прежняя |
| Повторный запуск | ничего не применяется |
| Состояние пользователей | число строк и хэш идентификаторов `users`, `participant_registrations`, `api_sessions`, `invoice_intents`, `payment_receipts`, `engagement_accounts`, `engagement_awards` и число отозванных доступов до и после `003` совпадают |
| Старый код после `003` | чтение и `INSERT … ON CONFLICT` в `beta_settings` — ошибка `42P01`: отсюда порядок выкладки ниже |

`tools/beta-settings-capture.sh` после `003` сообщает, что снимать нечего (код выхода 4).

### Порядок выкладки

API применяет миграции при старте своего контейнера, а `docker compose up -d` пересоздаёт
сервисы не одновременно. Если `003` приедет вместе с новым ботом, старый бот успеет обратиться
к удалённой таблице (`/api/state` → 503). Поэтому поставки две, и миграция в ветке — последний
коммит:

1. **Первая поставка** — ревизия без `db/migrations/003_drop_beta_settings.sql` (родитель
   коммита с миграцией). Перед ней в каждом контуре: `tools/beta-settings-capture.sh`, значение
   записать в `BETA_OPEN` env-файла, `docker compose --env-file … config --quiet`. Затем
   сборка и выкладка: бот читает список из env, таблица остаётся неиспользуемой. Проверка: dev
   Mini App показывает прежний туман.
2. **Вторая поставка** — ревизия с `003`. Сначала dev, затем prod; перед prod — резервная копия
   по [`environments.md`](environments.md) (`pg_dump -Fc` под `umask 077`, проверка кода
   завершения, пробное восстановление). Не продолжать, если копия не удалась.

Откат. Раннер идёт только вперёд. Вернуть таблицу можно новой миграцией `004_*` со структурой
из `002` и значением из раздела 02 либо восстановлением из резервной копии; вместе с этим
понадобится откатить код бота. Без отдельного решения владельца не делать.

Не выполнено: миграция к dev и prod не применялась, выкладка не проводилась.
