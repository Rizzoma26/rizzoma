# Архитектура модуля «Мир» по уровням сложности

Статус: рекомендация для реализации

Связанное ТЗ: [world-map-spec.md](world-map-spec.md)

Детализация:

- [модель данных](world-map-database.md);
- [TLS, mTLS и сертификаты](world-map-pki.md).

## 1. Основное решение

Для первой рабочей версии использовать **модульный монолит**:

```text
Telegram Mini App
        │
        ▼
React/TypeScript + MapLibre
        │ HTTPS JSON
        ▼
Node.js/TypeScript API
        │
        ▼
PostgreSQL + PostGIS
```

Статический клиент раздаётся через CDN. Изображения точек хранятся в S3-совместимом
объектном хранилище. Карта получает векторные тайлы от внешнего поставщика.

Существующие дерево и вкладка «Свои» не переписываются одним большим изменением. Новый
модуль «Мир» сначала монтируется как изолированный React-root, а общий Telegram adapter
выносится из `index.html`. Остальные части переносятся в модульную структуру только по
мере их изменения.

На старте не нужны:

- микросервисы;
- Kubernetes;
- Redis;
- брокер сообщений;
- отдельный сервис рейтинга;
- собственный сервер картографических тайлов;
- публичная административная панель;
- нейросеть внутри runtime приложения.

Это особенно важно для проекта, который будет в значительной степени разрабатываться
нейросетью: чем меньше скрытых связей и инфраструктурных слоёв, тем проще проверять
изменения и локализовать ошибки.

## 2. Уровни архитектурной сложности

### Уровень 0. Демонстрационный прототип

Сложность: низкая.

Состав:

- существующий статический `index.html`;
- карта и точки хранятся на клиенте;
- прогресс в `localStorage`;
- моковые QR и награды;
- без настоящего membership и серверного claim.

Подходит только для проверки дизайна и механики тумана на тестовых данных.

Не подходит для реального запуска: пользователь может увидеть скрытые координаты,
назначить себе награду и изменить прогресс через инструменты разработчика.

### Уровень 1. Безопасный MVP — рекомендуемый запуск

Сложность: средняя.

Состав:

- Vite + TypeScript + React для нового клиентского модуля;
- MapLibre для карты;
- Node.js + TypeScript API как модульный монолит;
- PostgreSQL + PostGIS;
- серверная проверка Telegram `initData`;
- серверный список участников;
- серверное хранение тумана, точек, QR, claims и наград;
- QR с непрозрачным случайным токеном;
- проверка членства, свежего GPS и расстояния 100 метров;
- уникальность claim на уровне БД;
- CLI для импорта точек и генерации QR;
- кэш ранее просмотренной карты;
- логи, метрики и резервные копии.

Уровень рассчитан на текущую задачу: 40–50 точек, около 2 000 участников и 20–25
одновременно активных пользователей.

### Уровень 2. Эксплуатационно зрелый продукт

Сложность: средняя/высокая.

Добавляется после успешного пилота:

- два и более экземпляра API за балансировщиком;
- Redis только для распределённого rate limit, кэша или коротких блокировок;
- отдельный worker для тяжёлого импорта, обработки изображений и массовых уведомлений;
- защищённая административная панель с ролями;
- несколько миров и расписания кампаний;
- централизованные логи и трассировка;
- автоматизированное восстановление из резервной копии;
- feature flags и поэтапное включение механик.

Переходить сюда нужно, когда появляется постоянная операционная команда, несколько
параллельных кампаний либо фактическая нагрузка, которую один API уже обрабатывает плохо.

### Уровень 3. Много городов и высокая нагрузка

Сложность: высокая.

Возможные дополнения:

- отдельная выдача геоданных по регионам и масштабам;
- PMTiles или собственная инфраструктура тайлов;
- фоновые очереди;
- read replicas БД;
- секционирование крупных таблиц discovery/ranking events;
- региональные CDN;
- отдельные контуры аналитики;
- управление сотнями миров и тысячами точек.

Для 50 точек и 25 активных пользователей этот уровень является преждевременным.

### Уровень 4. Награды высокой ценности и серьёзный антифрод

Сложность: очень высокая.

Добавляется, если получение точки даёт дорогой или ограниченный актив:

- динамический QR с коротким сроком жизни;
- QR, отображаемый сотрудником или специальным устройством;
- NFC/Bluetooth-маяк;
- дополнительное подтверждение сотрудником;
- анализ аномалий маршрута и повторяющихся устройств;
- лимиты по устройству и участнику;
- ручная очередь разбора спорных claims;
- нативное приложение и device attestation, если требуется более сильное доказательство
  физического присутствия.

Статический QR, Telegram membership и GPS в радиусе 100 метров дают разумную защиту MVP,
но не являются криптографическим доказательством нахождения у объекта.

## 3. Сложность отдельных функций

| Функция | Сложность | Комментарий |
|---|---:|---|
| Серая карта города | низкая | Готовый стиль и внешний поставщик тайлов |
| 40–50 маркеров | низкая | Один GeoJSON/WebGL-слой без сложной кластеризации |
| Карточка точки | низкая | Изображение, адрес, описание и статус |
| Telegram-авторизация | средняя | Требуется серверная HMAC-проверка и срок жизни сессии |
| Membership | низкая/средняя | Простая таблица допуска, сложность зависит от способа вступления |
| Туман по H3-ячейкам | средняя | Геометрия, синхронизация и мобильная производительность |
| Полное сокрытие точек | средняя | Сервер должен фильтровать данные по открытым ячейкам |
| Отслеживание при открытом Mini App | средняя | GPS, точность, паузы и редкие обновления |
| Фоновое отслеживание | очень высокая | В Telegram Mini App гарантировать нельзя; нужен native-клиент |
| Статический QR + GPS | средняя | Подходит для MVP при умеренной ценности награды |
| Транзакционный claim | средняя | Транзакция, unique constraint, idempotency |
| Набор скрытых наград | средняя | Награды не должны утекать до claim |
| Кэш просмотренных тайлов | средняя | Зависит от лицензии поставщика карт |
| Полная офлайн-карта Петербурга | высокая | Размер, лицензия, версии и загрузка пакетов |
| CLI-импорт точек | низкая/средняя | Dry-run, схема и идемпотентный upsert |
| Полноценная админка | средняя/высокая | Авторизация, роли, аудит и безопасные загрузки |
| Скрытый рейтинг | низкая | Хранятся факты; формула и UI отсутствуют |
| Динамический QR | высокая | Время, устройства показа и синхронизация |
| Антифрод маршрутов | высокая | Сложные правила, ложные срабатывания и разбор споров |

### Правила границ

- `apps/web` не импортирует код сервера и не знает структуру БД.
- `apps/api` не отдаёт модели БД напрямую наружу.
- `packages/contracts` содержит только безопасные публичные типы, схемы запросов и
  ответов, перечисления и коды ошибок.
- Доменные правила находятся в соответствующем серверном модуле, а не в HTTP-route.
- PostGIS-запросы изолированы в repository-слое.
- У каждого модуля есть явный публичный интерфейс; импорты во внутренние файлы другого
  модуля запрещены.
- Одна таблица БД не означает отдельный сервис.

## 5. Потоки данных

### 5.1. Авторизация

```text
Telegram initData
  → POST /auth/telegram
  → сервер проверяет HMAC и auth_date
  → проверяет/создаёт user
  → выдаёт короткоживущий access token
  → токен хранится только в памяти вкладки
```

После перезагрузки клиент заново обменивает `initData`. Долгоживущий access token не
хранится в `localStorage`.

### 5.2. Открытие тумана

```text
watchPosition
  → клиент фильтрует явно плохие образцы
  → отправляет небольшой batch
  → сервер проверяет membership, время, accuracy и правдоподобность перемещения
  → вычисляет H3-ячейки
  → записывает новые discovered_cells
  → возвращает новые ячейки и точки внутри них
```

Скрытые точки до этого ответа не находятся на клиенте.

### 5.3. Claim

```text
QR token + свежая геопозиция + idempotency key
  → auth
  → membership
  → QR active
  → point active
  → distance ≤ 100 м
  → accuracy/time accepted
  → DB transaction
       claim INSERT with unique(user_id, point_id)
       reward assignments INSERT
       ranking event INSERT
  → commit
  → безопасный ответ с раскрытой наградой
```

## 6. Минимальная модель угроз

### Угроза 1. Пользователь меняет данные клиента

Риск: назначает себе точку, прогресс или награду через консоль.

Защита: клиент никогда не является источником истины. Все изменения происходят только
через сервер и ограничения БД.

### Угроза 2. Неучастник вызывает API напрямую

Риск: получает карту или награду, имея ссылку на приложение.

Защита: каждый world/discovery/claim endpoint проверяет авторизацию и активный
`world_member`. Проверка только на клиенте запрещена.

### Угроза 3. Утечка скрытых точек

Риск: пользователь смотрит Network и получает координаты всех точек.

Защита: сервер не возвращает неоткрытые точки ни в каком публичном ответе, включая
агрегаты, ошибки и административные поля.

### Угроза 4. Подбор или подделка QR

Риск: последовательный `point_id` можно угадать.

Защита: случайный токен минимум 256 бит, в БД хранится хэш, сравнение выполняется на
сервере, токен можно отозвать. QR не содержит награду.

### Угроза 5. Повторный запрос и гонка

Риск: две параллельные отправки создают две награды.

Защита: DB-транзакция, уникальный индекс `(user_id, point_id)`, idempotency key и возврат
результата первого успешного claim.

### Угроза 6. Передача фотографии QR

Риск: другой участник использует фотографию.

Защита MVP: membership, свежая геопозиция и радиус 100 метров. Остаточный риск принят.
Для ценных наград применяется уровень 4: динамический QR/NFC/сотрудник.

### Угроза 7. Подмена GPS

Риск: программная эмуляция координат.

Защита MVP: свежесть, accuracy, максимальная скорость, отсутствие телепортаций,
сопоставление discovery и claim. Полностью исключить подмену в Mini App нельзя.

### Угроза 8. XSS через контент точки

Риск: описание или импортированное поле выполняет JavaScript у пользователей.

Защита: название, адрес и описание считаются обычным текстом; сырой HTML запрещён.
Если появится Markdown, он проходит строгий sanitizer. URL изображений проверяются, а
загрузки ограничиваются по MIME, размеру и разрешению.

### Угроза 9. Утечка секретов

Риск: токен бота, ключ БД или admin token попадает в клиент или Git.

Защита: секреты только в secret storage окружения; клиент получает только публичный
ограниченный ключ карт. Логи и ошибки не содержат секретов.

### Угроза 10. Перегрузка API

Риск: частые GPS-пакеты, сканирование и подбор токенов создают нагрузку.

Защита: лимит размера body, batch discovery, rate limit по Telegram user ID и IP,
ограничение частоты claim, таймауты БД и максимальное число элементов в ответе.

### Угроза 11. Потеря данных

Риск: ошибка миграции, оператора или диска удаляет прогресс.

Защита: ежедневные резервные копии, point-in-time recovery при доступности, проверка
восстановления, миграции сначала на staging и запрет ручного изменения production-БД.

## 7. Обязательный baseline безопасности

Следующие меры входят уже в уровень 1 и не откладываются «на потом»:

### Авторизация и доступ

- проверять HMAC Telegram `initData` на сервере;
- проверять `auth_date` и отклонять старые данные;
- использовать короткоживущую серверную сессию;
- применять deny-by-default к world и admin операциям;
- проверять membership на каждом защищённом endpoint;
- не доверять `initDataUnsafe` и полям клиента.

### HTTP и браузер

- только HTTPS;
- точный CORS allowlist, без `*` в production;
- security headers и CSP;
- запрет `unsafe-eval`;
- ограничение размера JSON body;
- единая безопасная схема ошибок без stack trace и SQL;
- описания точек рендерятся как текст, не через небезопасный `innerHTML`.

### API и БД

- runtime-валидация каждого входа и выхода;
- только параметризованные SQL-запросы;
- транзакции для claim;
- уникальные и внешние ключи в БД;
- отдельный runtime-пользователь БД без прав на миграции;
- миграции запускаются отдельной операцией;
- никакого прямого доступа клиента к БД;
- административные изменения пишутся в audit log.

### Секреты и данные

- токен бота, пароль БД и admin token не находятся в `config.js`;
- секреты не коммитятся и не печатаются в CI;
- QR хранится в виде хэша;
- сырой `initData`, QR, промокоды и координаты не попадают в логи;
- exploration location samples имеют короткий TTL, после чего остаются только H3-ячейки;
- claim хранит только данные, необходимые для аудита.

### Зависимости и поставка

- lock-файл обязательно коммитится;
- версии production-зависимостей фиксируются;
- CI запускает typecheck, lint, unit и integration tests;
- зависимости проверяются на известные уязвимости;
- production build создаётся в CI, а не вручную на сервере;
- dev/demo seed и QA-панель не включаются в production.

Текущий `.gitignore` исключает `package-lock.json`; перед переходом к npm workspaces это
правило необходимо удалить. Без lock-файла сборка неповторяема, а аудит зависимостей
менее надёжен.

## 8. Правила для разработки нейросетью

### 8.1. Архитектурные ограничения

- Одна кодовая база и один API до появления измеренной причины для разделения.
- Одна задача меняет один вертикальный сценарий и его тесты.
- Не создавать абстракцию до появления второго реального использования.
- Не создавать `utils` для доменных правил: правило принадлежит конкретному модулю.
- Не добавлять новую библиотеку без краткого объяснения, зачем недостаточно текущих.
- Не менять API-контракт и схему БД молча.
- Не смешивать рефакторинг и новую функциональность в одном большом изменении.
- Не генерировать миграции, удаляющие или переименовывающие production-данные без
  отдельного review.

### 8.2. Контракты как ограждение

- Все request/response схемы лежат в `packages/contracts`.
- Сервер валидирует запрос и ответ в runtime.
- Клиент генерирует или импортирует типы из тех же публичных контрактов.
- Изменение контракта сопровождается тестом совместимости.
- Коды ошибок стабильны и не зависят от текста сообщения.

### 8.3. Definition of Done

Изменение считается готовым, только если:

1. Описан пользовательский сценарий и отказные случаи.
2. Обновлён контракт API, если он затронут.
3. Добавлена миграция, если меняется БД.
4. Есть unit-тест доменного правила.
5. Есть integration-тест авторизации и БД для чувствительной операции.
6. Проверено, что ответ не раскрывает скрытые поля.
7. Typecheck, lint и тесты проходят.
8. Не добавлены секреты, персональные данные в логи или новая небезопасная зависимость.
9. Для UI проверены loading, empty, error, offline и retry состояния.

## 9. Обязательные тесты безопасности

До запуска должны автоматически проверяться:

- поддельный и просроченный Telegram `initData` отклоняется;
- неучастник не получает map-state;
- ответ не содержит скрытые координаты или reward bundle;
- пользователь не может открыть ячейку другого пользователя;
- отозванный QR отклоняется;
- QR другой точки не подходит;
- claim дальше 100 метров отклоняется;
- старая или неточная геопозиция отклоняется;
- два параллельных claims создают одну запись и один набор наград;
- повтор с тем же idempotency key возвращает прежний результат;
- описание точки не исполняется как HTML/JavaScript;
- oversized body и слишком частые запросы блокируются;
- stack trace, SQL и секреты не появляются в API-ответе;
- production-конфигурация не включает QA/admin доступ.

## 11. Триггеры перехода на следующий уровень

Переход с уровня 1 на уровень 2 нужен, если выполняется хотя бы одно условие:

- контент регулярно меняет отдельный менеджер;
- одновременно работают несколько кампаний;
- один API не выдерживает измеренную нагрузку;
- появляются тяжёлые фоновые операции;
- простой одного экземпляра становится неприемлемым;
- ручные CLI-операции становятся частыми и рискованными.

Переход на уровень 3 нужен при множестве городов, тысячах точек или значительном объёме
геоданных. Переход на уровень 4 определяется не количеством пользователей, а ценностью
награды и допустимым уровнем мошенничества.

## 12. Принятый остаточный риск MVP

На уровне 1 сознательно принимается следующее:

- Telegram Mini App не отслеживает пользователя в фоне;
- GPS можно подменить;
- статический QR можно сфотографировать;
- ранее не просмотренная карта требует сеть;
- при потере сети claim невозможен;
- точность GPS в плотной городской застройке может превышать 100 метров.

Эти риски не скрываются. Они проверяются полевым пилотом и усиливаются только тогда,
когда стоимость мошенничества или ошибок оправдывает уровень 4.
