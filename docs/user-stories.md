# Истории пользователей базового приложения

Scope: Telegram Mini App «дерево узлов», бот, tickets, engagement и dev/prod baseline.
Карта «Мир» намеренно исключена: для неё сохранён отдельный draft в `world-map-spec.md`.

**Статусы:** **Код** — требование видно в текущей реализации; **Demo** — работает только как
локальный fixture и не даёт серверных прав; **Runtime** — код готов к проверке, но настоящий
Telegram/провайдер/сервер в рамках этого review не проверялся.

## Вход и приглашения

### US-01 — Войти из своего бота

Как пользователь Telegram, я хочу открыть Mini App из бота и получить защищённую сессию,
чтобы мой профиль был связан с Telegram ID.

- Bootstrap отправляет подписанный `initData` API.
- При успешной проверке ставится `Secure`, `HttpOnly`, `SameSite=Strict` cookie.
- **Статус:** Runtime.

### US-02 — Повторно открыть уже авторизованное приложение

Как пользователь с активной cookie, я хочу вернуться в UI без повторной выдачи сессии,
чтобы повторная загрузка не создавала лишнее состояние.

- Bootstrap и `registration.js` проверяют `/api/v1/session`.
- Bootstrap и `registration.js` сверяют identity из `/api/v1/me` с текущим Telegram ID.
- Совпадающая сессия повторно используется; для другой учётной записи выполняется регистрация по подписанному `initData`.
- **Статус:** Код; защищённый домен требует runtime-проверки.

### US-03 — Отказать поддельному или устаревшему входу

Как владелец сервиса, я хочу проверять Telegram HMAC и возраст `initData` на сервере,
чтобы пользователь не мог назначить себе чужой Telegram ID.

- Невалидная подпись, формат или время завершаются отказом.
- Данные из `initDataUnsafe` не являются доказательством доступа.
- **Статус:** Код.

### US-04 — Ограничить dev тестерами

Как владелец dev-контура, я хочу пускать только allowlist Telegram ID,
чтобы dev-проверки не принимали случайных пользователей.

- allowlist проверяется сервером при регистрации и проверке сессии.
- в prod QA/dev allowlist не включается.
- **Статус:** Код; разделение двух реальных ботов — Runtime.

### US-05 — Сохранить один аккаунт из Mini App и бота

Как участник, я хочу, чтобы вход через приложение и `/start` обновлял один профиль,
а не создавал двух пользователей.

- `telegram_user_id` уникален; повторная регистрация обновляет существующую identity.
- первый валидный referrer остаётся закреплённым.
- **Статус:** Код.

### US-06 — Перейти по referral-ссылке

Как приглашённый пользователь, я хочу открыть ссылку с `startapp`/`ref`,
чтобы приложение и бот могли связать вход с кодом пригласившего.

- допустимая ссылка принимается только после проверки формата.
- самореферал игнорируется; attribution имеет ограниченный срок хранения.
- **Статус:** Код; начисление оплаченного приглашения — Runtime.

## Дерево и прогресс

### US-07 — Понять структуру наград

Как участник, я хочу видеть радиальное дерево и категории скиллов,
чтобы понимать, какие узлы относятся к билетам, вещам и VIP.

- дерево строится из существующей геометрии сцены и `TIERS`/`BRANCHES`.
- подписи и статус узла следуют масштабу и состоянию беты.
- **Статус:** Код.

### US-08 — Исследовать дерево на телефоне

Как пользователь сенсорного экрана, я хочу панорамировать и масштабировать поле,
чтобы добраться до дальних доступных узлов.

- поддержаны touch/pinch, колесо и движение камеры.
- интерфейс учитывает Telegram viewport и safe areas.
- **Статус:** Код; реальные устройства — Runtime.

### US-09 — Отличить закрытый узел от узла вне беты

Как участник, я хочу видеть разное объяснение для недостатка рефералов и закрытой беты,
чтобы не путать прогресс с ограничением доступа.

- «не хватает N» и «вне беты» имеют отдельные статусы и текст.
- узел вне беты не активируется удержанием.
- **Статус:** Код.

### US-10 — Посмотреть описание узла до получения

Как участник, я хочу открыть карточку доступного узла обычным нажатием,
чтобы понять его награду до подтверждения.

- tap открывает карточку; получение награды не происходит от одного tap.
- заблокированный узел не запускает действие удержания.
- **Статус:** Код.

### US-11 — Получить skill только один раз

Как участник, я хочу завершить удержание на доступном узле,
чтобы сохранить его в своём локальном прогрессе.

- `grantClaim` добавляет индекс один раз и сортирует список.
- повторный вызов не меняет localStorage и компактный claims cache.
- **Статус:** Demo; это не подтверждение серверной награды.

### US-12 — Восстановить локальный прогресс в Telegram

Как участник, я хочу подхватить сохранённые узел и claims на своём Telegram-аккаунте,
чтобы продолжить после переустановки или смены устройства.

- localStorage остаётся быстрым локальным кэшем.
- CloudStorage обменивается только определённым набором ключей и не превышает лимит ключа.
- **Статус:** Код; синхронизация в реальном Telegram — Runtime.

### US-13 — Использовать интерфейс при reduced motion

Как пользователь с настройкой уменьшения анимации, я хочу выполнять те же действия
без интенсивной анимации, чтобы приложение оставалось доступным.

- `prefers-reduced-motion` и `?reduce=1` упрощают motion, сохраняя действия.
- **Статус:** Код.

## Билеты и платежи

### US-14 — Открыть билеты из любого положения дерева

Как участник, я хочу открыть bottom sheet чекаута из плавающей кнопки,
чтобы не искать отдельный экран билетов.

- кнопка доступна при любом масштабе/положении дерева.
- в Telegram используются системные кнопки по назначению.
- **Статус:** Код; Telegram runtime — Runtime.

### US-15 — Выбрать класс и количество билетов

Как покупатель, я хочу выбрать тип билета и количество проходов,
чтобы сформировать подходящий счёт.

- UI передаёт класс и количество; клиент не передаёт доверенную сумму.
- **Статус:** Код.

### US-16 — Не платить по не объявленной цене

Как покупатель, я хочу видеть, что цена ещё не назначена,
чтобы приложение не выставляло случайную сумму.

- `price: null` блокирует оплату и отображает состояние «уточняется».
- сервер заново проверяет цену и состав счёта.
- **Статус:** Код.

### US-17 — Получить счёт от Telegram-провайдера

Как участник Telegram, я хочу получить invoice link для выбранного билета,
чтобы оплатить его штатным интерфейсом Telegram.

- сервер рассчитывает сумму и валюту, создаёт `invoice_intent`, затем запрашивает ссылку.
- ошибка хранилища/провайдера не отображается как успешная покупка.
- **Статус:** Runtime.

### US-18 — Зачесть оплату после подтверждения

Как участник, я хочу получить оплаченный статус после подтверждённого Telegram update,
чтобы клиент не мог сам объявить покупку успешной.

- `paid` ставится обработчиком `successful_payment` после сверки invoice и суммы.
- `/api/purchase` не подтверждает оплату.
- **Статус:** Код; live provider — Runtime.

### US-19 — Не засчитать повторный платёжный update

Как владелец сервиса, я хочу, чтобы повторная доставка одного charge не создавала
вторую оплату или второй узел.

- Telegram charge ID уникален в `payment_receipts`.
- тот же ID и тот же invoice возвращают результат без повторной вставки.
- несовпадающий invoice/user отклоняется.
- **Статус:** Код; Telegram redelivery — Runtime.

## Активность и вкладка «Свои»

### US-20 — Получать баллы за наблюдаемые события канала

Как участник канала, я хочу получать баллы за доступные Bot API события,
чтобы вклад отражался в приложении.

- источник события — Telegram update бота, не заявление браузера.
- баллы и события хранятся в PostgreSQL при включённом persistent store.
- **Статус:** Код; права бота в канале — Runtime.

### US-21 — Не получать баллы дважды за одно событие

Как участник, я хочу, чтобы повтор события не дублировал award,
чтобы счётчик отражал уникальные действия.

- award имеет dedup key и уникальный активный индекс.
- правила дневного лимита и повторов задаются в `engagement.js`.
- **Статус:** Код.

### US-22 — Понять отсутствие слежения за каналом

Как участник, я хочу отличить отключённый tracking от нуля баллов,
чтобы понимать, почему вклад не отображается.

- ответ API содержит состояние tracking.
- UI показывает разные состояния «не подключено», «ноль» и сумму.
- **Статус:** Код.

### US-23 — Видеть только собственные баллы

Как участник, я хочу получать свой ledger без доступа к чужим событиям,
чтобы данные активности оставались личными.

- Telegram ID берётся из проверенной identity, а не из тела запроса.
- **Статус:** Код; закрытый production-контур — Runtime.

### US-24 — Посмотреть приглашённых

Как участник, я хочу видеть ветвь, созданную referral-переходами,
чтобы понимать, кто пришёл по моей ссылке.

- список формируется из серверной referral-связи в bot store.
- приложение не запрашивает адресную книгу Telegram.
- **Статус:** Код.

### US-25 — Привязать аккаунт через бота

Как участник, я хочу связать Mini App и диалог с ботом,
чтобы использовать Telegram-сценарии приглашений.

- бот сопоставляет подписанную регистрацию и referral identity.
- **Статус:** Код; два аккаунта Telegram не использовались в этой проверке.

## Бета, QA и администрирование

### US-26 — Показать тестеру только открытую часть дерева

Как тестер, я хочу видеть список открытых узлов и ясное состояние остальных,
чтобы не принять закрытый раздел за ошибку приложения.

- beta-open приходит с сервера при доступном API и отрисовывается отдельно от прогресса.
- **Статус:** Код; фактический контур беты — Runtime.

### US-27 — Изменять глобальную бету только администратору

Как владелец беты, я хочу менять beta-open серверным запросом,
чтобы все участники видели одну конфигурацию.

- сервер сверяет Telegram identity с `ADMIN_TG_IDS`.
- локальный `config.js` не выдаёт право на живые данные.
- **Статус:** Код.

### US-28 — Отозвать допуск тестера

Как администратор, я хочу приостановить доступ участника,
чтобы заблокированный tester не продолжал использовать защищённый API.

- состояние отзыва сохраняется в PostgreSQL.
- защищённые запросы после отзыва отвергаются.
- **Статус:** Код.

### US-29 — Проверить локальную механику без живых данных

Как разработчик, я хочу открывать QA-панель в браузерном fixture,
чтобы проверять узлы, сброс и анимации без воздействия на prod.

- браузерная панель меняет только локальное demo-состояние.
- prod QA API выключен; dev доступ ограничен сервером.
- **Статус:** Demo + Код.

### US-30 — Экспортировать состояние fixture

Как тестировщик, я хочу выгрузить raw state и журнал действий,
чтобы повторить сценарий или передать дефект.

- экспорт относится к локальной тестовой панели.
- в него нельзя включать Telegram `initData`, токены или данные платежа.
- **Статус:** Код; экспорт нужно вручную проверить перед передачей.

## Эксплуатация

### US-31 — Не смешивать dev и prod

Как владелец сервиса, я хочу изолировать БД, сессии, секреты и бот-токены,
чтобы тестовые изменения не затрагивали пользователей.

- разные контуры используют собственные DB URL, volumes, cookie names и Telegram bot token.
- **Статус:** Код/конфигурация; инфраструктура deployment отдельно требует приёмки.

### US-32 — Узнать доступность API и базы

Как оператор, я хочу отдельно видеть liveness процесса и readiness PostgreSQL,
чтобы отличать процесс, который запущен, от готового обслуживать запросы.

- `/health/live` проверяет процесс; `/health/ready` — подключение к БД.
- **Статус:** Код.

### US-33 — Не применять миграцию второй раз

Как оператор, я хочу безопасно повторить запуск API,
чтобы повторный deploy не менял схему непредсказуемо.

- уже применённые миграции проверяются по checksum.
- SQL applied migration нельзя редактировать; новая схема получает новый файл.
- **Статус:** Код.

### US-34 — Не публиковать секреты в UI и логах

Как владелец, я хочу хранить bot/provider secrets только на сервере,
чтобы публичные статические файлы не выдавали credential.

- клиентский config содержит только публичные настройки.
- ошибки API логируются без тела запроса, `initData`, токенов и подписи.
- **Статус:** Код; секреты реального окружения здесь не проверялись.

### US-35 — Обновить web assets одним артефактом

Как оператор, я хочу, чтобы новые data-модули и SVG попадали в образ вместе с UI,
чтобы production не отдавал страницу без её ресурсов.

- Docker web stage копирует `assets/` целиком.
- URL SVG разрешается относительно страницы и проходит через защищённый web gate.
- **Статус:** Код; образ проверяется только на финальном шаге.

### US-36 — Получить повторную доставку Telegram update после сбоя

Как владелец бота, я хочу восстановить необработанный update после перезапуска,
чтобы не терять платёж или award.

- payment receipt защищён от дубля; long polling не имеет отдельного durable inbox.
- сценарий восстановления после рестарта нужно проверить в Telegram sandbox.
- **Статус:** Runtime/open risk.
