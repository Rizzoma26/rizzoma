# Контуры Rizzoma: dev и prod

Статус: **реальное развёртывание не выполнено**. В документе сохранён результат более ранней
локальной runtime-проверки; исходная запись не фиксировала commit SHA, поэтому её нельзя считать
проверкой текущего грязного checkout. 2026-09-28 для текущего дерева запускался только
`docker compose ... config --quiet` для dev/prod с временными URL-заглушками; сервисы не стартовали.
Документ не содержит реальных доменов и секретов.

## Решение

Один сервер обслуживает два независимых запуска того же приложения:

| Область | Dev | Prod |
|---|---|---|
| Назначение | Функциональная и QA-проверка | Реальные пользователи |
| Публичный адрес | Отдельный HTTPS-домен, пока не задан | Отдельный HTTPS-домен, пока не задан |
| Telegram | Второй бот, собственный токен и Mini App URL | Основной бот, собственный токен и Mini App URL |
| Runtime | Свои web, API, bot, PostgreSQL | Свои web, API, bot, PostgreSQL |
| Данные | Отдельная БД, sessions и volume; allowlist тестеров | Отдельная БД, sessions и volume |
| Оплата | Только тестовая конфигурация либо отключена | Боевая конфигурация после отдельного включения |
| QA-функции | По серверному разрешению | Выключены |

Один Telegram user ID может встретиться в обоих контурах, но аккаунты, регистрация, баллы, платежи и сессии не синхронизируются. Нельзя использовать общую БД или менять `DATABASE_URL` так, чтобы dev получил доступ к prod. PostgreSQL доступен только внутри своего контура; наружу выходит HTTPS-прокси. Разные Compose project names, networks, volumes и ограничения ресурсов предотвращают конфликт на одном сервере, но не делают сервер отказоустойчивым: его сбой затронет оба контура.

## Схема запросов

```text
prod HTTPS-домен ──┐          ┌── prod web ── prod API ── prod PostgreSQL
                   ├── proxy ─┤                  └── prod bot
dev HTTPS-домен ───┘          └── dev web ─── dev API ─── dev PostgreSQL
                                              └── dev bot
```

У каждого бота свой `APP_URL`; у каждого API — свой `BOT_TOKEN`, допустимый origin и собственное соединение с БД. Dev-бот не должен открывать prod, а prod-бот — dev. В текущей реализации бот получает обновления через long polling; два бота требуют двух разных токенов. TLS-сертификат должен покрывать оба домена; детали DNS и TLS-терминации выбираются после получения адресов.

## Закрытый вход

Приложение предназначено для входа через **Telegram Mini App**, а не для просмотра обычной страницей или встроенным браузером Telegram. Подписанный `Telegram.WebApp.initData` передаётся серверу, где проверяются подпись, время и пользователь. Для dev дополнительно проверяется серверный allowlist тестеров. Данные одного бота не должны проходить проверку API другого контура.

Начальный HTTP GET не несёт `initData`, поэтому маленькая стартовая страница для авторизации остаётся общедоступной. Это не полноценный сайт: основной интерфейс, защищённые статические ресурсы и API доступны только после создания серверной сессии. Без корректного входа показывается «Откройте приложение через бота». Проверка `window.Telegram`, `initDataUnsafe`, User-Agent или CORS не заменяет серверную авторизацию. Сессии dev/prod изолируются, имеют срок жизни и не передаются через URL.

## Выпуск и эксплуатация

1. Собирать один проверяемый артефакт из конкретного коммита. Сначала развернуть его на dev, проверить Mini App, бота, регистрацию, оплату в тестовом режиме и отрицательные сценарии доступа.
2. Перед prod сохранить резервную копию его PostgreSQL. Продвинуть ту же версию, применить миграции только к prod БД и выполнить короткую проверку работоспособности без тестовых платежей и QA-функций.
3. Держать env-файлы/секреты вне Git, ограничить доступ к серверу и журналам. Не копировать prod-данные в dev без отдельного решения об обезличивании. Следить за health/readiness, ошибками входа, ботом, БД и свободным местом под backups.

Миграции версионируются: уже применённый SQL не меняется. Изменения схемы, необходимые для обоих контуров, сначала проверяются на dev. При одной машине нужны лимиты ресурсов dev, чтобы его проверки не лишили prod памяти и CPU.

## Реализация и границы проверки

Compose использует имя `rizzoma-${APP_ENV}`: каждый запуск получает собственные network и PostgreSQL volume (`rizzoma-dev_rizzoma_postgres`, `rizzoma-prod_rizzoma_postgres`). API, bot и PostgreSQL не публикуют порты на хост. Web слушает только loopback: dev — 8082, prod — 8080. `SERVICE_MEMORY_LIMIT` и `SERVICE_CPUS` ограничивают каждый контейнер; значения нужно подобрать по ресурсам сервера.

Nginx публично отдаёт только bootstrap, его скрипт и `/healthz`. Bootstrap передаёт подписанный `initData` в `/api/v1/registrations/telegram`; после успешной проверки открывается защищённый `/app.html`. Все остальные статические файлы и `/api/*` бота требуют сессии; `/api/v1/*` проверяет её в API. Подписанный маршрут регистрации бота предназначен только для внутренней сети. `config.js` содержит публичные настройки, без токенов.

Cookie `__Host-rizzoma-dev` / `__Host-rizzoma-prod` имеет `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, без `Domain`. В БД хранится хеш случайного токена, API проверяет срок, отзыв и активность пользователя. Dev allowlist проверяется при входе, каждом запросе сессии и обработке событий бота. Изменение env требует пересоздания API и bot. Запуск без dev allowlist запрещён. Сессия по умолчанию живёт 900 секунд; возраст данных запуска при входе — максимум 300 секунд (допуск часов вперёд — 60 секунд). После истечения сессии приложение нужно заново открыть из бота; автоматическое продление не реализовано.

API отклоняет чужой Origin; bot API тоже проверяет Origin, сессию, подпись и совпадение Telegram ID. После входа bot API использует срок сессии, сохраняя проверку подписи и личности. Сессия — доказательство успешного Telegram-входа, а не постоянное доказательство того, какой браузер её предъявляет.

`QA_ENABLED=true` разрешён только в dev; дополнительно нужен `ADMIN_TG_IDS`, а администратор должен входить в dev allowlist. Платежи по умолчанию отключены. `PAYMENT_MODE=test` разрешён только dev с provider token `:TEST:`, `live` — только prod с `:LIVE:`; несовместимые настройки останавливают bot. При `disabled` новые счета и pre-checkout отклоняются, доставленные квитанции продолжают учитываться. Совместимость формата токена конкретного провайдера нужно проверить до включения оплаты.

**CONTRADICTION — наблюдаемое / документированное / принятое:** прежний README описывал публичный браузерный режим и независимый статический хостинг. В Docker теперь установлен серверный gate. Браузерный fallback остаётся только в исходном UI для локальных тестов; `npm run dev:web` слушает loopback и не является способом публичного размещения. GitHub Pages и отдельная раздача исходного `index.html` обходят эту архитектуру и не используются для dev/prod.

## Подготовка и выпуск

1. Создать вне Git `/etc/rizzoma/dev.env` и `/etc/rizzoma/prod.env` из `docker/dev.env.example` и `docker/prod.env.example`; права — 600. Задать разные bot token, пароли PostgreSQL, имена БД/пользователей и HTTPS origins. В каждом файле `APP_URL`, `ALLOWED_ORIGINS`, `BOT_CORS_ORIGIN` должны соответствовать одному домену. Пароль в `DATABASE_URL` кодируется по правилам URL. Не переопределять Compose project name общим `-p` или `COMPOSE_PROJECT_NAME`.
2. Выбрать чистый проверенный commit, записать его SHA в `RELEASE_TAG` обоих файлов. Проверить шаблоны без печати секретов и собрать образы один раз:

   ```bash
   docker compose --env-file /etc/rizzoma/dev.env config --quiet
   docker compose --env-file /etc/rizzoma/prod.env config --quiet
   docker compose --env-file /etc/rizzoma/dev.env build api bot web
   docker compose --env-file /etc/rizzoma/dev.env up -d --no-build
   docker compose --env-file /etc/rizzoma/dev.env ps
   ```

   Тег сам по себе не неизменяемый: не перезаписывать его новой сборкой. Зафиксировать image IDs/digests проверенных образов и использовать их же для prod. API сам применяет миграции перед запуском; уже применённый SQL не менять.
3. Настроить DNS и HTTPS-прокси на сервере. `docker/Caddyfile.example` — шаблон для Caddy на хосте; `DEV_DOMAIN` / `PROD_DOMAIN` содержат разные DNS-имена, без схемы. Он направляет запросы на loopback-порты web. Указать каждому боту свой HTTPS Mini App URL в BotFather. Если proxy запущен в контейнере, loopback из этого шаблона к хосту не ведёт — потребуется отдельная схема соединения. Ограничить доступ к журналам; не включать логирование cookies, тел запросов и query string.
4. Проверить dev по матрице ниже. Для существующего prod перед обновлением сохранить резервную копию; пример запускается на сервере из корня checkout:

   ```bash
   umask 077
   docker compose --env-file /etc/rizzoma/prod.env exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > /secure-backups/rizzoma-prod-before-release.dump
   docker compose --env-file /etc/rizzoma/prod.env up -d --no-build
   docker compose --env-file /etc/rizzoma/prod.env ps
   ```

   Каталог backups нужно создать с ограниченными правами; для каждого выпуска использовать новое имя файла, проверить код завершения `pg_dump` и восстановление в отдельную БД. На первом запуске prod резервной копии ещё нет. Не продолжать обновление после неудачного backup. Возврат старого image допустим только при совместимой схеме; volume не удалять.

## Приёмка перед внешним запуском

| Проверка | Ожидаемый результат |
|---|---|
| Dev Mini App, разрешённый Telegram ID | Вход, UI и API работают; запись только в dev PostgreSQL |
| Prod Mini App, тот же Telegram ID | Независимый профиль и состояние только в prod PostgreSQL |
| Dev Mini App, ID вне allowlist | 403, пользователь/сессия не создаются |
| Браузер или Telegram in-app browser без initData | Только приглашение открыть приложение из бота |
| Запрос `/app.html`, `/config.js`, `/api/v1/me`, bot API без cookie | 401/403; UI и данные не возвращаются |
| Чужой bot token, просроченная/поддельная подпись | Вход отклонён в обоих направлениях |
| Cookie dev на prod, в том числе с переименованием | Отклонена: отдельные cookie names и хранилища сессий |
| Истёкшая/отозванная сессия, заблокированный пользователь | Доступ к UI/API закрыт |
| Удаление из dev allowlist и пересоздание API/bot | Старая сессия больше не даёт доступ |
| Чужой Origin на операциях записи | 403 |
| QA на prod; live token на dev; test token на prod | QA недоступен; несовместимая конфигурация не запускается |
| Недоступный API/PostgreSQL | Защищённые ресурсы не открываются |
| Перезапуск dev, регистрация и изменение данных | Prod продолжает работать, его данные не меняются |

**Историческая запись предыдущего runtime-среза, SHA не сохранён:** локально `api`, `bot`, `web` и PostgreSQL были собраны и запущены двумя Compose projects с разными внутренними сетями и volumes. На каждом были заявлены 36 HTTP/SQL проверок через nginx: публичный bootstrap, закрытый UI/API, синтетическая Telegram-подпись, cookie, повторная регистрация, allowlist, сессии, Origin и QA. Оба контура применили две миграции. Проверка пересоздавала API и проверяла повторное разрешение адресов контейнеров nginx. Перед выпуском нужно повторить проверки на конкретном коммите.

Кроме того, при первом runtime запуске тест выявил неоднозначный PostgreSQL параметр в регистрации (`42P08`); к параметрам `first_source` добавлен явный тип, после чего регистрация и повторный вход прошли в обеих БД. Для не-root nginx временные каталоги FastCGI, uWSGI и SCGI перенесены в `/tmp`. Docker build и runtime проверки подтверждают запуск local images и синтетические проверки, но не настоящую доставку Telegram updates: в контейнере QA long polling заменён тестовой заглушкой. Браузерный обмен cookie по внешнему домену, реальные Mini Apps двух ботов и платежи не проверялись. До такой проверки внешний deployment не считается принятым.

## Необходимые данные перед реальным запуском

- Два домена и DNS-записи на сервер.
- Два действующих Telegram bot token, заданных только в секретах сервера; раскрытые токены ротировать до внешнего доступа.
- Список Telegram ID тестеров dev и решение, включать ли тестовый платёжный провайдер.
- Доступ к серверу, способ TLS-терминации, резервного копирования и хранения секретов.

До появления этих данных можно готовить код, Compose-шаблоны и проверки, но нельзя считать Mini App запущенным на телефонах.
