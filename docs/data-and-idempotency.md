# Данные и повторные операции

Этот документ описывает текущую Mini App-ветку. Старые клиентские ключи оставлены ради
совместимости; изменение их формата требует отдельной миграции клиента.

## Сущности и владельцы

| Сущность | Поля/смысл | Место модели | Хранение и доверие |
|---|---|---|---|
| `DemoUser` | Код узла, имя/email, paid-флаг демо, referrer, список приглашённых, время создания | `assets/js/data/entities.js` | localStorage; пользователь может изменить данные |
| `DemoDatabase` | `users`, `buyers`, `profiles`, `claims` | `assets/js/data/entities.js` | localStorage; fixture/offline-кэш, не серверный источник истины |
| Attribution | `code`, `ts`, TTL 30 дней | `assets/js/data/client-state-repository.js` | localStorage и необязательная копия CloudStorage |
| Skill claims | индексы полученных узлов | `assets/js/data/client-state-repository.js` | localStorage + CloudStorage; claim повторно не добавляется |
| Engagement snapshot | `points`, события и флаги доступности | `assets/js/data/entities.js` | localStorage-кэш; начисления вычисляет бот и хранит PostgreSQL |
| `UserRecord`, `RegistrationRecord` | серверный пользователь и результат регистрации | `apps/api/src/auth/auth.models.ts` | передаются через API; это не строковые модели БД |
| PostgreSQL rows | колонночные представления и SQL-маппинг | частные интерфейсы в `auth.repository.ts`, запросы в `bot/storage.js` | PostgreSQL; схема определяется только SQL-миграциями |
| HTTP DTO | валидируемые запросы/ответы регистрации | `packages/contracts/src/index.ts` | общий контракт Mini App, API и бота |

База на клиенте остаётся plain JSON: без прототипов и методов, чтобы старые значения
продолжали читаться. Entity-фабрики задают значения по умолчанию и форму записи; репозиторий
владеет доступом к localStorage/Telegram CloudStorage. UI может менять отображаемые профили,
но сохранение проходит через отдельный репозиторий.

## Стабильные ключи клиента

| Ключ | Содержимое | CloudStorage |
|---|---|---|
| `rizzoma_mock_db` | `{users, buyers, profiles, claims}` | да, если размер не больше лимита API |
| `rizzoma_me` | код текущего узла | да |
| `rizzoma_attribution` | `{code, ts}` | да |
| `rizzoma_claims` | компактный `{code, list}` | да |
| `rizzoma_beta` | список открытых узлов | нет; сервер перекрывает при доступности |
| `rizzoma_engagement` | кэш последнего ответа баллов | нет; сервер перекрывает при доступности |

## Серверная схема

`db/migrations/001_identity.sql` задаёт `users`, `participant_registrations` и `api_sessions`.
`002_persistent_bot_state.sql` добавляет `invoice_intents`, `payment_receipts`,
`engagement_accounts`, `engagement_awards` и единственную строку `beta_settings`.
Уже применённые файлы миграций неизменяемы. Runner блокирует конкурентное применение,
сравнивает checksum и пропускает совпавшую миграцию.

## Гарантии повторного выполнения

| Действие | Наблюдаемая гарантия | Ограничение |
|---|---|---|
| Применить миграции снова | checksum совпал — SQL не выполняется повторно | Проверка на живой PostgreSQL требует runtime-среды |
| Зарегистрировать Telegram ID ещё раз | `users.telegram_user_id` уникален; upsert возвращает ту же identity, регистрация хранит первый валидный referrer | Каждая новая успешная регистрация без действующей cookie может выдать отдельную короткую сессию |
| Повторно открыть Mini App | `bootstrap.js` и `registration.js` проверяют `/api/v1/session`, сверяют `/api/v1/me` с текущим Telegram ID и переиспользуют только совпадающую сессию | При сетевой ошибке проверки выполняется попытка регистрации; после восстановления возможна новая сессия |
| Повторно обработать платёжный update | `telegram_payment_charge_id` уникален; совпавший charge не вставляет вторую квитанцию и не начисляет прогресс снова | Реальная доставка update не проверена в этой задаче |
| Повторно начислить событие активности | уникальный активный `(telegram_user_id, dedup_key)` блокирует дубль | Отозванную награду можно начислить снова по правилам приложения |
| Повторно выдать skill claim | `grantClaim` проверяет наличие индекса до записи; повтор не меняет JSON | Это локальное состояние, а не доказательство права на награду |
| Повторно объединить claim cache | список дедуплицируется, фильтруется до индексов `0..9` и сортируется; повторный merge не перезаписывает кэш | CloudStorage — асинхронное зеркало, не транзакционная реплика |
| Повторно сохранить `betaOpen` | список нормализуется, удаляются дубликаты, задаётся стабильная сортировка | Серверное состояние беты остаётся авторитетным в Telegram-контуре |

## Ограничения локального слоя

localStorage синхронен в пределах одного origin, но не обеспечивает транзакцию между
устройствами или между браузером и Telegram CloudStorage. CloudStorage может быть недоступен,
ограничен по размеру или вернуть устаревшее значение; приложение продолжает работу с локальным
кэшем. При наличии API ответ `/api/state` заменяет серверные поля пользователя, а `/api/engagement`
— сумму баллов. Клиентские `paid`, `refs`, beta и claims не должны становиться авторитетом
для выдачи платной награды.
